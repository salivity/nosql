How Graph Databases Parallelize Multi-Hop Traversals

This article examines how distributed and multi-core graph NoSQL query engines parallelize multi-hop graph traversals. Multi-hop queries—such as finding relationships \(N\) degrees away—suffer from exponential search space expansion and memory latency bottlenecks. Graph engines mitigate these challenges by combining frontier-based data parallelism, balanced graph partitioning, asynchronous execution runtimes, and distributed state management to scale traversals across threads and network clusters.

The Core Challenge: Frontier Explosion

A multi-hop traversal begins at a set of start vertices (hop 0) and sequentially retrieves adjacent neighbors across successive hops (\(k = 1, 2, \dots, n\)). In real-world graphs characterized by power-law degree distributions, the number of visited nodes can grow exponentially with each hop. Additionally, high-degree vertices (supernodes) create computational skew, where a single vertex can monopolize execution resources. To execute these traversals efficiently, graph engines treat the set of nodes at each hop as an active "frontier" and divide the frontier's expansion across processing units.

Frontier Partitioning and Data Parallelism

Graph engines parallelize neighbor lookups primarily through data-parallel frontier expansion. Instead of processing entire traversal paths serially via deep-first search (DFS), engines switch to breadth-first search (BFS) or iterative deepening:

  1. Chunked Task Scheduling: The active frontier is split into smaller chunks and placed into thread-safe work queues. Worker threads process these chunks concurrently by scanning the adjacency lists of the vertices within their assigned chunk.
  2. Work-Stealing Runtimes: Because vertex degrees vary wildly, static distribution of vertices leads to thread starvation. Modern engines use work-stealing schedulers (similar to Java ForkJoin or C++ TBB) where idle threads steal frontier chunks or individual adjacency segments from overloaded threads.

Graph Partitioning Across Distributed Nodes

In distributed NoSQL graph databases, adjacency data cannot fit on a single machine. The engine must minimize inter-node network roundtrips during traversal hops:

  • Vertex-Cut Partitioning: Traditional edge-cut partitioning (cutting edges across servers) causes supernodes to generate massive network traffic when traversed. Vertex-cut partitioning splits high-degree vertices across multiple machines while keeping edges local. During a multi-hop hop, the engine expands local edges concurrently on all mirror nodes and synchronizes the aggregate frontier afterward.
  • Locality-Aware Hashing: Vertices and their immediate outgoing edges are placed on nodes using consistent hashing. When a traversal step must traverse remote edges, queries are batched by destination node ID to convert millions of tiny remote lookups into bulk network requests.

Execution Models: BSP vs. Asynchronous Pipelining

Distributed graph engines employ two primary computational models for multi-hop expansion:

Bulk Synchronous Parallel (BSP)

Engines following the BSP model (such as Apache Giraph or Google Pregel) execute multi-hop queries in discrete global stages (supersteps):

  1. Compute: Every node processes its portion of the current frontier concurrently.
  2. Communication: Nodes exchange messages containing the destination vertex IDs for the next hop.
  3. Barrier Synchronization: Execution halts until all nodes finish message exchange.
  4. Advance: The received messages form the next frontier, and the process repeats for hop \(k+1\).

BSP guarantees deterministic execution and simplifies state tracking, but the slowest machine or highest-degree node acts as a barrier straggler.

Asynchronous and Pipelined Traversal

Engines like Neo4j (Fabric), Amazon Neptune, and JanusGraph often favor pipelined or actor-based asynchronous processing:

  • Stream-Based Pipelining: As soon as a worker thread discovers neighbors for a portion of the frontier, it pushes them directly into downstream operators without waiting for the global hop to complete.
  • Direction-Optimizing Traversals: For dense frontiers, engines alternate between "push" (active vertices send messages to all neighbors) and "pull" (unvisited vertices check if any neighbor is in the active frontier) models to reduce message overhead and maximize parallel throughput.

Parallel Visited-State and Cycle Tracking

Multi-hop traversals require cycle detection to prevent infinite loops and redundant computation. Maintaining a shared "visited" set across parallel threads presents a significant synchronization bottleneck:

  • Lock-Free Concurrent Bitsets: On single-node multi-core engines, visited sets are maintained as shared, cache-aligned, lock-free bit arrays (or Roaring Bitmaps). Threads mark nodes as visited using atomic operations (CAS or atomic bitwise OR), eliminating lock contention.
  • Distributed Bloom Filters and Partitioned Hash Sets: In distributed settings, each machine maintains a local visited filter for the vertices it owns. During message exchange, target nodes consult their local sets to prune already-visited vertices before adding them to the local processing queue for the next hop.
