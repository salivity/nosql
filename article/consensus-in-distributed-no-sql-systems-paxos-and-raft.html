Consensus in Distributed NoSQL Systems: Paxos and Raft

Distributed NoSQL systems rely on consensus algorithms like Paxos and Raft to maintain a consistent, synchronized state across multiple independent nodes despite hardware failures and network partitions. This article examines how these databases implement State Machine Replication, handle leader election and quorum-based log replication, resolve conflicting write operations, and navigate the practical trade-offs between consistency and operational latency.

The Problem of Distributed Consensus

In a distributed NoSQL database, data is partitioned and replicated across multiple physical machines to ensure high availability and horizontal scalability. When a client issues a write request, all replicas must agree on the order and value of that write.

Without a coordination mechanism, concurrent writes and network partitions can cause replicas to diverge, resulting in split-brain scenarios where different nodes claim authority over the same data. Consensus algorithms solve this by ensuring that a cluster of nodes can agree on a sequence of operations as long as a majority (a quorum) of nodes remains operational.

State Machine Replication

Both Paxos and Raft implement consensus through State Machine Replication (SMR). Under SMR:

  1. Every replica acts as an identical deterministic state machine.
  2. An append-only log records all incoming state transitions (writes).
  3. If all replicas process the same inputs in the exact same sequence, they will inevitably arrive at the same internal state.

The role of the consensus algorithm is not to manage the database storage engine directly, but to guarantee that the replicated logs on all participating nodes remain identical in content and order.

Paxos in NoSQL Systems

Classic Paxos achieves consensus on a single value through a two-phase protocol:

  1. Prepare/Promise Phase: A proposer node selects a unique proposal number \(n\) and sends a Prepare(n) message to a majority of acceptors. If an acceptor receives a proposal number higher than any it has previously observed, it responds with a Promise not to accept proposals numbered lower than \(n\), returning any previously accepted value.
  2. Propose/Accept Phase: Once the proposer receives promises from a quorum, it sends an Accept(n, value) message. The value is either the one returned by the acceptors in phase one (if any) or a new value. If the acceptors have not promised to ignore proposal \(n\), they accept it.

Because basic Paxos requires two round-trips per write, production NoSQL engines use Multi-Paxos. Multi-Paxos elects a stable leader to bypass the prepare phase for subsequent writes, reducing latency to a single round-trip under normal conditions.

For instance, Apache Cassandra utilizes a variant of Paxos for its Lightweight Transactions (LWT), allowing linearizable compare-and-set operations across distributed nodes.

Raft in NoSQL Systems

Raft was designed to provide the same guarantees as Multi-Paxos while being more understandable by decomposing consensus into three explicit sub-problems: leader election, log replication, and safety.

1. Leader Election

A Raft cluster operates with one elected leader and multiple followers. If followers stop receiving periodic heartbeats from the leader due to network delays or crashes, an election timeout triggers. A follower transitions to a candidate state, increments its term counter, votes for itself, and requests votes from peers. A candidate becomes the leader if it secures votes from a strict majority (\(N/2 + 1\)) of the nodes.

2. Log Replication

Once elected, the leader handles all client writes:

  • The leader appends the write as a new entry in its local log.
  • It distributes the entry to follower nodes via AppendEntries remote procedure calls (RPCs).
  • Once a majority of followers acknowledge writing the entry to their local disks, the leader commits the entry and applies it to its local state machine.
  • The leader notifies followers of the commit in subsequent RPCs, and the followers apply the entry locally.

3. Safety Invariants

Raft enforces log matching properties to ensure consistency:

  • If two entries in different logs have the same index and term, they store the identical command.
  • If two entries in different logs have the same index and term, their logs are identical up to that point.
  • Candidates cannot be elected unless their log is at least as up-to-date as the majority of the cluster, preventing committed entries from being overwritten.

Modern distributed datastores such as CockroachDB, TiDB, and etcd rely on Raft (or Raft-based multi-group designs) to coordinate transaction state and metadata catalogs.

Quorums and Failure Recovery

Both algorithms rely on overlapping majorities. If a cluster contains \(2f + 1\) nodes, it can tolerate \(f\) simultaneous failures. Because any two majorities share at least one node, the most up-to-date node is always present in any quorum formed to elect a leader or commit an entry.

During node recovery, catching up is achieved by synchronizing missing log indices from the current leader. If an offline node lags significantly behind, transferring individual log entries becomes inefficient. In such cases, the leader generates and streams a snapshot of the state machine, allowing the follower to fast-forward its state before rejoining real-time consensus.

Latency and Architectural Trade-offs

Achieving strict consensus introduces unavoidable overhead:

  • Write Amplification and Latency: Writes require network round-trips to reach a majority of nodes, along with synchronous disk writes (fsync) to persist log entries before acknowledgment.
  • Geographic Constraints: Multi-region deployments face latency penalties dictated by the speed of light between regions during the consensus phase.
  • Availability Impacts: If a network partition isolates more than half of the nodes, the minority partition cannot form a quorum and must reject writes to protect consistency, directly conforming to the CP constraints of the CAP theorem.
