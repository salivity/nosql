How NoSQL Engines Implement LRU and LFU Eviction

NoSQL key-value engines rely on eviction policies to maintain high throughput and low latency when dataset sizes exceed available RAM. This article explores how modern key-value stores move beyond textbook data structures to implement Least Recently Used (LRU) and Least Frequently Used (LFU) algorithms, detailing exact vs. approximated implementations, memory reduction techniques, and concurrency optimizations.

The Challenge of Native Implementations

In traditional computer science theory, an LRU cache is implemented using a hash map paired with a doubly linked list. Every read or write operation moves the accessed node to the head of the list, and evictions simply remove the node at the tail. Both operations run in \(O(1)\) time complexity.

However, high-throughput NoSQL engines (such as Redis, Memcached, and Aerospike) rarely use exact linked-list implementations for two main reasons:

  1. Memory Overhead: A doubly linked list requires two 64-bit pointers (prev and next) per entry, consuming an additional 16 bytes of memory per key. In systems storing hundreds of millions of small values, this overhead represents a massive percentage of total RAM.
  2. Lock Contention: In a multi-threaded or concurrent pipeline, moving an element to the head on every read requires modifying pointers. This converts concurrent read operations into mutating operations that necessitate exclusive locks, severely degrading read throughput.

Approximated LRU in Production

To eliminate memory and concurrency bottlenecks, production key-value stores use approximated (sampled) algorithms.

Sampled LRU Architecture

Instead of tracking absolute order via pointers, engines store a timestamp or an idle-time clock directly inside the key's metadata header.

  • Redis: Redis allocates 24 bits in the robj structure for an LRU clock. A global server clock updates periodically. When a key is accessed, its internal clock is updated to match the global clock.
  • The Eviction Cycle: When memory exceeds maxmemory:
    1. The engine selects a configurable random sample of keys (typically 5 to 10).
    2. It calculates the idle time for each sampled key by subtracting the key's LRU timestamp from the current global clock.
    3. The key with the highest idle time is evicted.

Eviction Pools

Modern versions of Redis improve this approximation using an eviction pool. The eviction pool is an array of candidate keys sorted by idle time. When a sample of keys is evaluated, qualifying keys are inserted into the pool. The engine consistently evicts the best candidate from the pool rather than purely from the instant sample, achieving behavior virtually indistinguishable from true LRU without the pointer overhead.

Implementing LFU: Handling Frequency and Decay

LFU evicts items with the lowest access count. A naive LFU implementation that merely increments an integer counter suffers from two primary issues: counter saturation (integers running out of bits) and "cache pollution" (historical popularity preventing newly popular items from remaining cached).

Probabilistic Counting (Morris Counters)

NoSQL engines solve the bit-overhead problem using logarithmic or probabilistic counters. Redis, for example, compresses LFU tracking into the exact same 24 bits used for LRU:

  • 16 bits: Last decay time (timestamp).
  • 8 bits: Logarithmic access counter (Logistic Counter).

An 8-bit counter can only count up to 255 if incremented linearly. With probabilistic counting, the counter increments based on a probability inversely proportional to the current counter value:

\[\Delta = \frac{1}{\text{counter} \times \text{lfu\_log\_factor} + 1}\]

As the counter increases, the probability of it incrementing decreases, allowing an 8-bit field to represent millions of accesses.

Counter Decay

To solve cache pollution, the access count must decay over time:

  1. When a key is accessed, the engine reads the 16-bit decay time.
  2. It calculates how many time intervals (e.g., minutes) have passed since the last access.
  3. The counter is decremented proportional to the elapsed time before the access logic is processed.

During an eviction pass, the engine samples keys just as it does in approximated LRU, but selects the key with the lowest decayed counter for removal.

Concurrency and Threading Optimizations

Handling eviction in multi-core architectures requires decoupling cache tracking from execution paths:

  • Batched Buffer Updates: High-performance engines like Caffeine and modern distributed caches avoid locking on reads by writing access events to a lock-free, bounded ring buffer. Background eviction threads read these ring buffers in batches to update LRU/LFU lists asynchronously.
  • Partitioned LRU: Memcached partitions memory into "Slab Classes" based on item size. Eviction operates independently within individual slab classes, preventing small keys from contending for eviction with large values.
  • Clock (Second Chance) Algorithm: Other engines implement variations of the Clock algorithm, treating memory pages or keys as a circular buffer. A single "used" bit is evaluated: if the bit is 1, it is set to 0 and skipped; if the bit is 0, the item is selected for eviction. This avoids global locking and list reordering altogether.
