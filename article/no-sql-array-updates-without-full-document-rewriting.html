NoSQL Array Updates Without Full Document Rewriting

Modern document-oriented NoSQL databases avoid rewriting entire documents during array modifications by combining granular update operators, low-level delta logging, and adaptive storage engine designs. Instead of replacing the full record on disk, these databases use specialized mechanisms—such as in-place byte manipulation, internal memory padding, and Write-Ahead Logging (WAL) of delta changes—to process array appends, removals, and element modifications with minimal I/O overhead.

Granular Path-Based Operators

Document databases like MongoDB rely on specialized operators (such as $push, $pull, and $set on indexed paths) rather than naive read-modify-write cycles from the application client. When an update request is received:

  • The database parses the target field path (for example, tags.2 or items.$[]).
  • It executes the change exclusively on the designated array offset in memory.
  • The update is serialized over the network and processed internally as an operational delta rather than a full document payload, significantly reducing network and CPU deserialization overhead.

Storage Engine Delta Logging and the WAL

At the durability layer, storage engines (such as WiredTiger in MongoDB or RocksDB in distributed variants) record updates via transaction journals or Write-Ahead Logs (WAL).

When an array grows or shrinks, the engine does not rewrite the complete BSON or JSON document to the journal. Instead, it writes a compact log record that captures only the specific array mutation. During periodic checkpoints, these changes are reconciled in memory and flushed to disk blocks, ensuring ACID guarantees without synchronous, full-document disk flushes.

In-Place Updates vs. Block Reallocation

How an array update is written directly to disk depends on the storage architecture:

  1. In-Place Updates with Padding: If an array element is modified without increasing its byte size (or if the document has pre-allocated padding space), the storage engine updates the bytes directly inside the existing disk page.
  2. Page-Level Buffering: Storage engines organize data into fixed-size memory pages (often 4KB to 32KB). When an array expands, the document expands within that allocated page. As long as the page has sufficient contiguous free space, the engine shifts neighboring bytes inside the page cache to fit the new array elements, avoiding a cross-disk rewrite.
  3. Log-Structured Merge (LSM) Trees: In LSM-based document stores, updates do not modify existing data blocks at all. Array mutations are written sequentially as new entries (tombstones or delta fragments) at the head of the log. Background compaction later merges these fragmented array states into a single unified document.

Handling Unbounded Array Growth

When dynamic arrays expand beyond the capacity of an existing storage block or page:

  • Document Relocation: If a document exceeds its current page bounds, the storage engine relocates the document to a larger continuous space. To prevent costly index updates across the entire database, the engine often leaves a lightweight pointer (forwarding address) at the original record ID, maintaining existing index pointers.
  • Out-of-Line Storage: For massive arrays that approach maximum document size thresholds (such as MongoDB's 16MB limit), architectures generally offload data into separate collection links or bucket patterns, as excessive continuous relocation causes disk fragmentation and CPU throttling.
