How NoSQL Databases Index Polymorphic Data Structures

Document NoSQL databases handle polymorphic data structures—where documents within the same collection feature distinct fields, varying nesting depths, or different data types—by leveraging flexible, path-based indexing techniques. Rather than enforcing a static table-wide schema, these systems use mechanisms such as wildcard indexing, sparse indexes, multi-key indexes, and schema-discriminator strategies. This article examines the core architectural methods document stores employ to efficiently index and query heterogeneous documents without sacrificing performance or flexibility.

1. Dynamic Path and Wildcard Indexing

In traditional relational databases, an index must map to a predefined column. In contrast, document databases like MongoDB, Amazon DocumentDB, and Couchbase utilize path-based indexing. Every element in a JSON or BSON document can be addressed via dot notation (e.g., attributes.color).

Wildcard indexes extend this capability by allowing the engine to index any arbitrary or unknown field within a document or subdocument:

  • Arbitrary Keys: By specifying a wildcard path (such as $**), the database automatically indexes all scalar fields within a nested document, regardless of the key names.
  • Subtree Indexing: Wildcards can be restricted to specific sub-objects (e.g., custom_attributes.$**), ensuring unpredictable metadata can be queried without indexing the entire document payload.
  • Internal Representation: The storage engine flattens paths into index keys composed of (Path, Value, DocumentID). When a query targets a dynamic attribute, the engine uses this composite key to find matching documents.

2. Sparse and Partial Indexes

Polymorphic collections often contain fields present in only a fraction of the documents. Indexing these fields across the entire collection using traditional methods creates bloated indexes filled with null values.

  • Sparse Indexes: A sparse index only includes entries for documents that actually contain the indexed field. Documents lacking the key are omitted from the index tree entirely, significantly reducing index size and write overhead.
  • Partial Indexes: Partial indexes use a filter expression (e.g., { "type": "electronic" }) to index fields conditionally. This allows distinct schemas to maintain distinct, highly optimized indexes on the same underlying collection.

3. Schema Discriminator Patterns

A common software pattern for polymorphic data is assigning a "discriminator" field (such as type, kind, or _class) to declare which schema variation a document adheres to.

Database engines optimize queries over this pattern via compound indexes where the discriminator is the leading key:

  • Index Structure: An index on { "type": 1, "specificAttribute": 1 } partitions the index tree logically by subtype.
  • Execution: Queries targeting a specific polymorphic type immediately skip irrelevant document branches, mitigating the scan penalty associated with heterogeneous collections.

4. Multi-Key Indexes for Array Polymorphism

Polymorphic documents frequently represent variable attributes as arrays of key-value pairs (e.g., [{ "k": "voltage", "v": 220 }, { "k": "wireless", "v": true }]).

To query these structures efficiently:

  • Document engines employ multi-key indexes, creating separate index entries for every element in the array.
  • Compound multi-key indexes on attributes.k and attributes.v allow queries to match on arbitrary dynamic attributes without needing unique fields for every possible property.

5. Inverted Indexing and Lucene-Based Engines

Databases such as Couchbase (with Global Secondary Indexes) and search-oriented document stores like Elasticsearch handle polymorphism by treating documents as collections of terms.

  • The database flattens JSON hierarchies into unique path-value pairs.
  • These pairs are stored in an inverted index, which maps every unique field:value combination directly to a list of internal document IDs.
  • When document schemas diverge completely, the inverted index simply absorbs new field paths as new lexicon entries, enabling performant equality, range, and full-text searches across structurally divergent records.
