NoSQL Index Selectivity on Unstructured Data

Query planners in NoSQL databases face a unique challenge when estimating index selectivity on unstructured and semi-structured fields due to the absence of rigid schemas, dynamic typing, and sparse data distributions. To select the most efficient execution plan without full-collection scans, NoSQL engines rely on dynamic sampling, path-aware frequency histograms, probabilistic data sketches, runtime execution feedback, and field-existence metrics. This article breaks down these primary techniques, explaining how modern document and multi-model database planners accurately predict query costs over unpredictable data structures.

Dynamic and Background Sampling

Unlike relational databases that maintain static table catalogs, NoSQL systems often inspect the underlying data dynamically. Query engines employ background workers or on-the-fly reservoir sampling to gather a representative subset of documents.

By analyzing this sample, the planner identifies:

  • The frequency of a targeted field across the collection.
  • Value distribution ranges (min, max, and quantiles).
  • Data type variations within the same field name.

This statistical snapshot allows the engine to compute a baseline selectivity factor for filter predicates without imposing high I/O overhead on production workloads.

Path-Indexed Histograms and Tries

In unstructured data formats like JSON or BSON, fields often exist at arbitrary nesting depths or within variable-length arrays. Query planners address this by constructing path-aware histograms using trie or prefix-tree data structures.

Instead of tracking values globally, the database indexes the full canonical path (for example, metadata.tags[] or order.items.sku). The engine maintains equi-depth or equi-width histograms specific to that complete path. When a query targets a nested attribute, the planner traverses the path tree to find the corresponding value-distribution histogram, yielding a localized selectivity estimate that accounts for structural nesting.

Probabilistic Data Sketches (HyperLogLog and Count-Min)

Storing complete value distributions for sparse, highly variable keys consumes excessive memory. Modern NoSQL query planners integrate probabilistic data structures (sketches) to estimate selectivity with bounded error margins and minimal footprints:

  • HyperLogLog (HLL): Used to compute the cardinality (distinct count) of dynamic keys. If an equality predicate targets a field with high cardinality relative to the collection size, the planner assigns it high selectivity.
  • Count-Min Sketch: Functions as a frequency table to detect heavy hitters (frequently occurring values) versus rare values. If a query filters on a "heavy hitter," the planner lowers the selectivity estimate, potentially favoring a collection scan over an index scan.

Field-Existence and Type-Distribution Profiling

In schemaless models, a query filter implicitly carries an existence check; a field might only appear in 5% of all documents. Therefore, NoSQL planners decompose selectivity into two distinct probabilities:

\[\text{Selectivity} = P(\text{Field Exists}) \times P(\text{Value Matches} \mid \text{Field Exists})\]

Planners record metadata regarding the sparsity of a field. If a field rarely exists, the index on that field will be highly selective regardless of value distribution. Additionally, because fields can hold polymorphic types (such as integers in some documents and strings in others), planners track the type breakdown. Predicates matching a minority type for that field are immediately flagged as highly selective.

Adaptive Query Execution and Feedback Loops

When static heuristics fail due to schema drift or skewed data, planners rely on runtime feedback loops. When an index scan executes, the database engine compares the estimated number of returned documents with the actual count observed by the storage engine.

If the planner significantly under- or over-estimated the selectivity, it records this variance in a plan cache. Subsequent query compilations targeting the same field or path apply a corrective dampening factor to the historical selectivity estimate, allowing the planner to self-correct dynamically as data shapes evolve.
