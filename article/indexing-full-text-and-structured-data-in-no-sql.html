Indexing Full Text and Structured Data in NoSQL

Search-oriented NoSQL databases—such as Elasticsearch, OpenSearch, and MongoDB with search integrations—simultaneously index free-form text and structured metadata by decoupling the data into specialized internal structures. Rather than relying on a single data layout, these engines break an incoming document down into individual fields during ingestion. Unstructured text is transformed into inverted indexes for linguistic matching, while structured payload data (such as numbers, dates, and enums) is written to columnar structures optimized for filtering, sorting, and aggregation. A shared, internal document identifier links these heterogeneous structures together, allowing the engine to execute hybrid queries with minimal latency.

Field-Level Parsing and Type Mapping

When a NoSQL database ingests a document, the ingestion pipeline analyzes the JSON schema to separate full-text attributes from structured payload attributes.

  • Text Fields: Fields designated for text search are routed to an analysis engine. The engine tokenizes the string into individual words, normalizes them (e.g., lowercasing, accent removal), and filters them through stemmers or stop-word dictionaries.
  • Structured Fields: Fields such as integers, timestamps, booleans, and exact strings (keywords) bypass linguistic analysis. They retain their literal scalar values and are mapped directly to structures optimized for discrete matching and range evaluation.

Inverted Indexes for Full-Text Search

Text tokens are written to an inverted index. This structure functions like an index at the back of a book, mapping individual terms to a list of internal document IDs (DocIDs) where those terms appear.

Along with the DocID, the inverted index stores positional offsets and term frequencies. These metadata markers enable phrase matching (checking if "data" immediately follows "structured") and relevance scoring algorithms, such as BM25, which calculate how strongly a document matches a natural language query based on token distribution.

Columnar Stores and BKD Trees for Structured Payloads

Structured payload data requires fast comparison operations rather than linguistic relevance. Search-oriented engines store structured data in two primary secondary structures:

  1. Doc Values (Columnar Storage): Instead of saving records row by row, the database groups structured field values column-by-column on disk. This enables sequential memory reads when sorting search results or calculating real-time aggregations (such as finding the average price of matched items).
  2. BKD Trees (Multi-Dimensional Trees): For numeric, date, and geospatial coordinates, engines frequently use block k-d (BKD) trees. This index structures data hierarchically, enabling fast sub-linear time lookups for range queries (e.g., timestamps between two dates).

Bridging Indexes via Shared Internal Document IDs

The inverted index and the structured data stores operate in parallel, synchronized through an auto-incrementing, compact internal DocID. Every segment of data uses the same local DocID to reference a specific record.

When a query contains both text search and structured filters (e.g., searching for the word "database" where status == 'active' and price < 50), the query engine utilizes bitsets or iterators:

  1. The engine checks the BKD tree or keyword index to identify DocIDs matching the structured criteria, returning a compact bitset where matching IDs are marked as 1.
  2. Simultaneously, the engine evaluates the inverted index for the term "database," producing an iterator of matching DocIDs.
  3. The engine performs a bitwise AND operation across these sets, discarding non-matching documents before computing expensive relevance scores. Only the surviving documents are ranked.

The Stored Payload (Source Document)

In addition to search-optimized indexes, search-oriented NoSQL databases preserve the original structured document in a compressed, row-oriented store (often referred to as the stored fields or _source).

Once the query engine uses the inverted index and columnar structures to find and rank the top matching DocIDs, it retrieves the full structured payload from this compressed store. This separation guarantees that search indexes remain lightweight and memory-efficient while still allowing the system to return complete, complex JSON payloads to the client.
