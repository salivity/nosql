NoSQL Memory Paging: When Keys Exceed RAM Limits

This article examines how key-value NoSQL databases handle memory paging and data retrieval when the cumulative volume of keys surpasses physical RAM capacity. When keys no longer fit in memory, databases must abandon all-in-memory index designs and instead adopt hybrid storage architectures. The following sections explore the mechanisms engines use to page, cache, and navigate large key spaces, including Log-Structured Merge-tree (LSM) sparse indexes, block-level caching, operating system paging abstractions, and prefix compression.

The Problem of Massive Key Spaces

In basic key-value designs, engines keep a full hash map of all keys in RAM to achieve \(O(1)\) lookups, directing disk heads only to fetch the corresponding payload values. When the aggregate size of the keys themselves exceeds the system’s physical memory, this architecture fails. The database cannot store every key in an active memory table without triggering operating system out-of-memory (OOM) errors or heavy swap thrashing. To operate within strict RAM limits, the storage engine must treat keys as secondary storage citizens, keeping only a fraction of key metadata in active memory and paging the rest from disk on demand.

LSM-Trees and Sparse Key Indexing

Engines utilizing Log-Structured Merge-trees (LSM-trees)—such as RocksDB and Apache Cassandra—solve the memory constraint by organizing data sequentially into Immutable Sorted String Tables (SSTables) on disk. Rather than indexing every key in RAM, LSM-trees apply sparse indexing:

  1. SSTable Block Partitioning: Data (keys and values) is sorted and divided into fixed-size disk blocks (typically 4 KB to 64 KB).
  2. Sparse In-Memory Index: Only the first (or last) key of each block is stored in an in-memory index, acting as a boundary marker.
  3. Paging via Block Caches: When a query targets a key, the database consults the sparse index to identify the specific block containing that key range. The engine reads that specific block from storage into a user-space LRU/2Q block cache.

Because the RAM footprint is reduced to just one index entry per block rather than one per key, key storage overhead in memory drops by orders of magnitude. Keys that are not actively queried remain paged out on disk.

B-Tree Derivatives and Buffer Pool Paging

Engines based on B-Trees or B+ Trees (such as MongoDB's WiredTiger or Couchbase's ForestDB) structure both keys and values into tree nodes, where internal nodes store search keys and leaf nodes store the target records.

  • Buffer Pools: The engine allocates a dedicated memory buffer pool that holds a subset of these tree nodes.
  • On-Demand Node Paging: If a lookup traversal hits a child node that is not present in the buffer pool, the engine initiates a synchronous I/O read to fetch the 4 KB or 8 KB page from disk.
  • Eviction Policies: When the buffer pool fills up, eviction algorithms like Least Recently Used (LRU) or Clock Sweep write modified (dirty) pages back to disk and evict clean pages to free memory for incoming key pages.

By handling the index as a set of fixed-size disk pages rather than a continuous memory array, B-tree implementations ensure that index depth increases while the working memory footprint remains bounded.

Memory-Mapped Files (mmap)

Some key-value engines, such as LMDB, offload paging mechanics entirely to the operating system kernel using the mmap system call. The entire database file—containing keys, pointers, and data—is mapped into the process's 64-bit virtual address space.

When the application accesses a virtual address referencing a key that is not in physical RAM, the CPU triggers a page fault. The operating system kernel intercepts this fault, retrieves the corresponding 4 KB page from disk into the OS page cache, updates the page tables, and resumes execution. When memory pressure rises, the OS kernel's virtual memory manager automatically pages out inactive key-bearing pages. While this simplifies the database engine, it provides less deterministic control over read-ahead and eviction strategies compared to dedicated user-space buffer managers.

Minimizing In-Memory Footprints

To reduce how frequently keys must be fetched from disk, modern engines use key compression and probabilistic filters:

  • Prefix and Delta Encoding: Within SSTable data blocks and B-Tree pages, keys are sorted alphabetically. Engines store only the shared prefix length and suffix difference relative to the preceding key, drastically reducing the disk and cache footprints of long keys.
  • Bloom Filters: To avoid paging in entire key blocks from disk during lookup misses, engines generate compact, in-memory Bloom filters for each SSTable. If the filter indicates a key is absent, the engine avoids reading that block from storage entirely, conserving both memory bandwidth and I/O cycles.
