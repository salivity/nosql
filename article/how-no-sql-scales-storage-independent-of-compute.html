How NoSQL Scales Storage Independent of Compute

Modern distributed applications frequently experience asymmetric resource demands where data volume grows significantly faster than processing requirements. While traditional NoSQL engines relied on tightly coupled shared-nothing architectures—requiring organizations to provision expensive compute nodes simply to acquire more disk space—modern systems decouple these layers. By isolating stateless execution engines from persistent data layers, modern NoSQL databases allow storage to scale to petabytes on low-cost media while compute resources dynamically resize based on real-time query throughput.

Disaggregated Storage Architecture

The foundational mechanism enabling independent scaling is disaggregation: physically separating processing nodes from persistent media across high-speed network fabrics. Instead of binding data partitions to local solid-state drives, modern NoSQL databases write data to shared distributed file systems, network-attached block stores, or cloud object stores (such as Amazon S3, Google Cloud Storage, or Ceph). Because the underlying storage system functions as an elastic, multi-tenant utility, database nodes do not own physical disks; they access an effectively infinite remote storage layer over standard network protocols.

Stateless Query and Processing Nodes

To divorce compute from storage, database processing engines are redesigned to be largely stateless. Nodes responsible for parsing queries, executing aggregations, coordinating transactions, and routing requests do not maintain persistent copies of partition data. If write traffic spikes, an operator can provision dozens of additional compute nodes that immediately begin processing operations without undergoing lengthy data rebalancing or partition copying. Conversely, during low-activity periods, compute capacity can be scaled down to near zero while the stored data remains untouched and durable in the underlying storage pool.

Immutable Data Formats and LSM-Trees

Many NoSQL databases rely on Log-Structured Merge-trees (LSM-trees) or append-only commit logs, which fit naturally into decoupled architectures. Write operations are first collected in transient compute-tier memory buffers (memtables) and write-ahead logs. Once these buffers reach capacity, they are flushed to storage as immutable data files (such as SSTables or Parquet-like columnar chunks). Because these files are read-only and never modified in place, they can be safely stored on cloud object storage. New data creates new files, and compaction processes merge files asynchronously in the background—often offloaded to dedicated background workers rather than user-facing compute nodes.

Decoupled Metadata Catalogs

Decoupled systems rely on a centralized or consensus-driven metadata catalog to map database keyspaces to specific files located in remote storage. Systems like FoundationDB or dedicated Raft-based clusters maintain the manifest of which SSTables contain which key ranges. When a compute node needs to process a query, it queries this metadata layer to identify the exact files it needs to read from the storage pool. This design ensures that compute nodes can be spun up or down dynamically, as any node can read any part of the dataset simply by consulting the global metadata layer.

Intelligent Ephemeral Caching

Because reading data over a network adds latency compared to local disk access, decoupled NoSQL engines implement multi-tiered caching strategies. Compute nodes utilize high-speed local RAM and local NVMe drives purely as ephemeral caches for hot data and index blocks. If a compute node terminates, no data is lost because the local drive contains only transient cache entries. The primary source of truth remains the remote storage tier, allowing compute instances to be treated as disposable, fungible assets that scale strictly on demand.
