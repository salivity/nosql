Role of Memtables and SSTables in NoSQL Storage

Memtables and Sorted String Tables (SSTables) are the foundational building blocks of Log-Structured Merge-tree (LSM-tree) storage architectures used by distributed NoSQL databases like Apache Cassandra, RocksDB, and ScyllaDB. This article explores how these two data structures operate in tandem to deliver high-throughput write performance, guarantee data durability, and manage the lifecycle of data from fast volatile memory to persistent disk storage.

The Role of the Memtable

A memtable (memory table) is an in-memory, write-buffering data structure. When a write, update, or delete request enters an LSM-based NoSQL system, the database routes the data to the memtable after recording it in a sequential Write-Ahead Log (WAL) for crash recovery.

Key roles and characteristics of the memtable include:

  • In-Memory Sorting: As writes arrive, the memtable stores them in sorted order by key, typically using data structures like skip lists, red-black trees, or AVL trees. Maintaining sorted data in memory removes the need for costly in-place random disk writes.
  • Low-Latency Writes: Because operations occur entirely in RAM, the write path achieves microsecond-level latency.
  • Serving Recent Reads: The memtable serves as the first stop for read queries. Because it contains the freshest version of newly written data, queries can often be resolved directly from memory without disk access.

The Role of the SSTable

An SSTable (Sorted String Table) is an immutable, on-disk storage format that holds key-value pairs sorted by key. Once a memtable reaches a predefined size threshold or time limit, the database freezes it, creates a new active memtable for incoming writes, and flushes the frozen memtable to disk as a new SSTable.

Key roles and characteristics of SSTables include:

  • Sequential Disk I/O: Because the memtable is already sorted, flushing to an SSTable requires only sequential writes, which maximizes disk throughput on both hard disk drives (HDDs) and solid-state drives (SSDs).
  • Immutability: SSTables are never modified in place. Immutability eliminates concurrency issues, locks, and complex transaction management for disk reads, while simplifying background replication and backups.
  • Auxiliary Data Structures: To optimize reads across multiple SSTables, databases pair SSTables with auxiliary structures:
    • Bloom Filters: Fast, probabilistic in-memory filters that determine whether a specific key definitely does not exist in an SSTable, preventing unnecessary disk seeks.
    • Partition Indexes: Index files that map key ranges to specific block offsets within the SSTable data file.

How Memtables and SSTables Work Together

The coordination between memtables and SSTables governs the core read and write paths in LSM-tree systems:

  1. The Write Path: Writes are sequentially appended to the commit log (WAL) on disk and inserted into the active memtable. No existing SSTables are read or updated during a write, which ensures sustained high write throughput.
  2. The Flush Process: When a memtable fills up, it transitions to a read-only state and is asynchronously written to disk as a base SSTable file. Once flushed, the corresponding segment of the WAL is discarded.
  3. The Read Path: Reads first check the active and flushing memtables. If the requested key is not present, the system checks SSTables from newest to oldest, using Bloom filters to skip non-relevant SSTables and indexes to locate the exact data block within valid SSTables.
  4. Compaction: Over time, flushes produce numerous SSTables containing duplicate updates, outdated records, and tombstones (markers for deleted data). A background compaction process reads multiple sorted SSTables, merges them by resolving conflicts using the latest timestamps, discards deleted records, and writes out consolidated, sorted SSTables. This prevents read degradation and reclaims disk space.
