How Graph Databases Handle Node Deletion

Graph NoSQL databases rely on index-free adjacency, where nodes maintain direct physical or logical memory references to their connected edges. When a node is deleted, leaving these pointer references intact causes dangling pointers and storage corruption. To handle deletions safely, graph engines employ several core strategies: mandatory cascading edge deletions, transactional two-phase locks, tombstone-based soft deletion with asynchronous compaction, and doubly linked relationship chains.

Cascade Deletion Requirements

Most native graph engines (such as Neo4j) enforce referential integrity by prohibiting the deletion of a node that still has attached relationships. If a user attempts to remove a node without removing its edges, the engine aborts the transaction with a constraint violation.

To delete a node successfully, systems execute an explicit cascade—often triggered via commands like DETACH DELETE. Under this process:

  1. The database reads the node's pointer head for its relationship chain.
  2. It traverses all incoming and outgoing edge records connected to the node.
  3. It de-allocates or unlinks those edge records from the opposing adjacent nodes.
  4. Finally, it removes the target node record itself.

Updating Doubly Linked Relationship Chains

In native graph storage formats, relationships are typically structured as doubly linked lists. An edge record stores pointers to:

  • The source node and target node.
  • The next and previous relationship pointers for the source node.
  • The next and previous relationship pointers for the target node.

When a node and its edges are removed, the database updates the adjacent surviving nodes. The storage engine rewrites the next or previous pointers of the surrounding edges in the surviving node's relationship list to skip the edge being removed, mimicking standard linked-list item deletion. If the deleted edge was the list head, the node record's pointer is updated to point directly to the subsequent edge.

ACID Transactions and Pessimistic Locking

To prevent race conditions where another query attempts to traverse an edge while its target node is being purged, graph databases use transactional isolation:

  • Exclusive Locks: The engine places an exclusive write lock on the target node, all incident edges, and the neighboring nodes connected to those edges.
  • Atomic Operations: All pointer updates across the affected nodes and edges are written to a Write-Ahead Log (WAL) or transaction journal before being applied to the storage files.
  • If a failure occurs mid-operation, the WAL rolls back the pointer updates, preventing orphaned or broken memory addresses.

Tombstoning and Asynchronous Garbage Collection

Non-native or distributed graph databases (such as those built on top of LSM-tree key-value stores like RocksDB or Cassandra) often avoid immediate physical pointer rewrites due to the high I/O cost of random writes:

  • Tombstones: The system writes a deletion marker ("tombstone") over the node's key.
  • Read-Time Filtering: When a traversal crosses an edge to a tombstoned node, the query engine detects the tombstone and discards that traversal path dynamically.
  • Compaction: During background storage compaction, the engine scans the data files, physically removes the tombstoned nodes, and purges any edge keys that reference the deleted node ID.

Memory ID Recycling Safeguards

Graph databases assign unique record IDs to nodes, which directly correspond to file offsets. When a node is deleted, its record slot is marked as free for reuse. To prevent existing references from mistakenly pointing to new data that reoccupies that slot, databases retain generation counters or cycle IDs. If an operation reads a record whose generation counter does not match the pointer's expected generation, the database invalidates the traversal rather than loading corrupted data.
