How Key-Value NoSQL Stores Implement Pub-Sub

Key-value NoSQL stores frequently include native publish-subscribe (pub-sub) messaging to provide real-time streaming capabilities alongside ultra-fast data retrieval without requiring external message brokers. While traditionally optimized for distinct point lookups via hash indexes or Log-Structured Merge (LSM) trees, these databases adapt their internal architectures to route messages from publishers to subscribers. This article examines the core mechanisms key-value engines use to implement native pub-sub, including in-memory client registries, append-only log primitives, non-blocking network I/O, and distributed message routing across clusters.

In-Memory Channel Registries

The most common implementation of transient pub-sub (exemplified by Redis) relies entirely on memory-resident hash tables rather than disk-backed key spaces.

  1. Channel Mappings: The database maintains an internal dictionary where keys represent channel names, and values are linked lists or sets containing references to active client network connections.
  2. Direct Memory Fan-Out: When a client issues a publish command, the engine looks up the channel in the dictionary and iterates through the associated list of client sockets. The payload is written directly to each socket's output buffer.
  3. Bypassing the Storage Engine: Because transient pub-sub does not persist messages, the data never touches the underlying key-value storage engine, write-ahead logs (WAL), or cache eviction layers. This results in minimal latency, though it introduces a "fire-and-forget" model where offline subscribers permanently miss messages.

Pattern Matching via Trie and Radix Structures

To support wildcard subscriptions (such as subscribing to news.*), key-value systems maintain a separate registry alongside the exact-match dictionary.

This is typically implemented using a linked list of patterns or a prefix tree (trie). When a message is published, the server performs an exact lookup on the channel dictionary and sequentially or structurally traverses the pattern tree. Any pattern matching the target channel causes the server to route a copy of the message to the corresponding client sockets.

Event-Driven Connection Management

Pub-sub requires persistent, stateful connections between subscribers and the database. Key-value stores leverage non-blocking I/O multiplexing primitives—such as epoll on Linux, kqueue on BSD/macOS, or completion ports on Windows—to handle thousands of concurrent subscriber connections within a single-threaded or low-threaded event loop.

When a client enters subscriber mode, the database transitions the connection state to listen-only. The server pauses command processing for that specific connection, keeping the TCP socket open indefinitely with negligible CPU overhead until a message triggers a socket write.

Persistent Pub-Sub via Append-Only Logs

Modern key-value databases also implement durable pub-sub patterns through append-only log data structures (such as Redis Streams).

Unlike transient pub-sub, this approach uses the primary storage engine:

  • Log Representation: Each channel or stream is modeled as an append-only collection of entries ordered by a monotonically increasing timestamp or sequence ID.
  • Consumer Tracking: The database stores metadata regarding consumer groups and read offsets directly in the key-value structure. Subscribers request messages starting from a specific ID.
  • Blocking Read Commands: If no new data is present, the storage engine registers the client in a waiting queue. Once an append operation occurs, the database identifies blocked clients waiting on that log and serves the appended entries, combining traditional database durability with streaming delivery.

Cluster-Wide Message Propagation

In distributed or sharded key-value stores, clients may be connected to different nodes across the cluster. Key-value engines handle cross-node message routing through two primary approaches:

  • Cluster Broadcasting: In early distributed pub-sub topologies, publishing to any node causes that node to broadcast the message across an internal cluster bus to every other node in the network. Each node then delivers the message to its locally connected subscribers. While simple, this approach scales poorly because network traffic increases linearly with the number of nodes regardless of whether remote nodes have active subscribers.
  • Sharded Pub-Sub: Advanced implementations bind pub-sub channels to the database's existing partition hash ring. A channel is hashed to a specific slot just like a standard key. Publishers and subscribers are routed to the specific node owning that hash slot, confining message traffic to the responsible shard and eliminating broadcast overhead across the cluster.
