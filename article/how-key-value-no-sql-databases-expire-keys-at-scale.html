How Key-Value NoSQL Databases Expire Keys at Scale

Key-value NoSQL databases manage key expiration (TTL) across massive datasets by combining passive expiration, active background sweeping, and storage-engine-level pruning during compaction. Instead of maintaining high-overhead global timers for every key, engines like Redis, Memcached, Aerospike, and RocksDB balance CPU utilization and memory footprint through probabilistic scanning and lazy evaluation. This article examines the core mechanisms these databases use to evict expired data efficiently without degrading read and write throughput.

Passive (Lazy) Expiration

Passive expiration is the least resource-intensive enforcement strategy. In this model, the database does not actively track when a key expires. Instead, it checks the key's TTL metadata only when a client sends a read or update request for that specific key.

If the current system timestamp exceeds the key's expiration timestamp, the engine marks the key as expired, removes it from memory or storage, and returns a cache miss or null response to the client. While this method requires virtually zero background CPU overhead, it cannot be relied upon exclusively. Abandoned keys that are never read again would reside in memory indefinitely, resulting in memory leaks over time.

Active Probabilistic Sweeping

To reclaim memory from keys that are never accessed again, databases implement active background eviction routines. Tracking millions of individual timers in a priority queue or min-heap introduces \(O(\log N)\) overhead that becomes prohibitive at scale. Consequently, engines often rely on randomized, probabilistic sampling.

Redis, for instance, runs an active eviction loop (typically 10 to 100 times per second) using the following cycle:

  1. Sample a small batch of keys that have an associated TTL (e.g., 20 random keys).
  2. Evict all sampled keys that have expired.
  3. If the percentage of expired keys in the sample exceeds a specific threshold (e.g., 25%), repeat the process immediately.

This adaptive loop ensures that the database aggressively purges keys when a large wave of expirations occurs, while conserving CPU cycles when the overall expiration rate is low.

Compaction-Time Pruning in LSM-Trees

For disk-backed NoSQL databases that use Log-Structured Merge-trees (LSM-trees)—such as Apache Cassandra, ScyllaDB, and RocksDB—expirations are handled asynchronously during storage maintenance.

Writes and updates in LSM-tree architectures are appended sequentially to memory (MemTables) and flushed to immutable disk files (SSTables). Instead of executing in-place deletions, these databases append expiration timestamps or deletion markers (tombstones). When background compaction merges multiple SSTables to reclaim disk space, it evaluates the expiration timestamps and drops the obsolete data entirely, avoiding random disk I/O.

Bucket-Based and Ring Buffer Partitioning

Some high-throughput databases organize expiring data into discrete time buckets, often implemented via hierarchical timing wheels or ring buffers.

Keys are categorized based on their expiration epoch (for example, partitioned into one-minute or one-hour ranges). When a time bucket elapses, the engine drops the entire partition or unlinks the bucket's underlying memory block in an \(O(1)\) operation. This bulk-eviction design eliminates the need to inspect or delete individual keys one by one, making it ideal for session management and ephemeral time-series workloads.
