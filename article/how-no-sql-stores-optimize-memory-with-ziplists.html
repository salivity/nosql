How NoSQL Stores Optimize Memory with Ziplists

In-memory key-value NoSQL stores, such as Redis, face substantial memory overhead when using standard pointer-based data structures to manage small collections. To solve this, databases employ compact, sequential byte arrays known as ziplists (and their modern derivatives, listpacks) that encode multiple elements into a single contiguous block of memory. This article explains how ziplists eliminate pointer overhead and memory fragmentation, details their internal architecture, and outlines the performance trade-offs databases manage when balancing low memory usage against CPU consumption.

The Problem with Traditional Data Structures

Standard implementations of data structures—such as doubly linked lists, hash tables, and skiplists—rely heavily on pointers. In a 64-bit architecture:

  • Every memory pointer consumes 8 bytes.
  • A standard doubly linked list node requires two pointers (16 bytes) plus memory allocator overhead (typically 8 to 16 bytes per allocation via malloc).
  • Storing a 2-byte integer inside a standard linked-list node can easily consume 32 to 48 bytes of actual RAM.

In addition to pure byte overhead, allocating thousands of tiny, disjoint nodes across the heap causes severe memory fragmentation and poor CPU cache locality, degrading system performance.

How a Ziplist Works

A ziplist replaces individual pointer-linked nodes with a single contiguous block of allocated memory. Instead of storing references to the locations of adjacent elements, the ziplist serializes items end-to-end using variable-length prefixes.

A complete ziplist structure typically consists of:

  • zlbytes (32 bits): An unsigned integer holding the total number of bytes consumed by the ziplist, allowing for fast resizing and bounds checking.
  • zltail (32 bits): The byte offset to the last entry, allowing \(O(1)\) access to the tail without traversing the entire list.
  • zllen (16 bits): The total number of entries stored.
  • entries: The variable-length payload elements.
  • zlend (8 bits): A dedicated byte (usually 0xFF) marking the end of the data structure.

Anatomy of an Individual Entry

Each entry inside a ziplist does not contain memory addresses. Instead, it contains three tightly packed fields:

  1. Previous Entry Length (prevlen): Encodes the size of the preceding element using either 1 byte (for lengths under 254 bytes) or 5 bytes (for larger lengths). This allows the database to traverse the list backward from tail to head without backward pointers.
  2. Encoding: A variable-length field indicating the data type (string or integer) and the length of the current payload. Small integers are frequently inlined directly into the encoding bits to save additional space.
  3. Data: The raw bytes of the string or binary representation of the integer.

By dynamically sizing metadata bytes based on the actual payload length, the structure virtually eliminates unused space.

Memory Optimization Benefits

  • Zero Pointer Overhead: Removing memory addresses saves 16 bytes per element compared to traditional bidirectional nodes.
  • Single Allocation: The entire list is stored in a single buffer. This removes the per-allocation metadata overhead enforced by memory allocators like jemalloc or glibc.
  • CPU Cache Efficiency: Because data is contiguous in memory, sequential iterations load whole chunks of elements into the CPU L1/L2 cache lines simultaneously, minimizing cache misses.

The CPU vs. Memory Trade-Off

While ziplists achieve remarkable compression, they are not suited for all workloads due to computational overhead:

  • Copy and Resize Costs: Every insertion or deletion requires a memory reallocation (realloc) and shifts existing bytes, turning operations that are \(O(1)\) in linked lists into \(O(N)\) operations.
  • Cascading Updates: In rare cases, changing the size of an element can cause the next element's prevlen field to expand from 1 byte to 5 bytes, potentially triggering a chain reaction of reallocations down the array.

Threshold-Based Conversion

To balance memory savings and computational latency, NoSQL engines apply ziplists conditionally. A key-value store monitors both the number of elements and the size of individual values (e.g., maximum 512 entries and 64 bytes per entry). While within these thresholds, the key uses the compact ziplist representation. Once a limit is breached, the engine transparently converts the compact structure into a traditional hash table, skiplist, or a hybrid structure (such as a quicklist, which links multiple small ziplists together).
