NoSQL Write Buffer Flushing and Disk Performance

Wide-column NoSQL databases like Apache Cassandra and ScyllaDB rely on Log-Structured Merge-tree (LSM-tree) architectures to achieve massive write throughput. Balancing the flushing of in-memory write buffers with physical disk performance is critical to prevent I/O saturation, manage latency spikes, and protect system stability. This article explains how these storage engines coordinate in-memory structures, asynchronous disk writes, backpressure controls, and compaction scheduling to maintain sustained hardware efficiency.

In-Memory Buffering with Memtables

When a write enters a wide-column NoSQL engine, it is processed in two steps: it is appended sequentially to a durable Commit Log on disk for crash recovery, and it is inserted into an in-memory sorted structure known as a Memtable.

Because Memtables reside entirely in RAM, the write path avoids immediate random disk I/O, allowing incoming operations to be acknowledged almost instantaneously. However, memory is finite. When a Memtable exceeds configured memory thresholds, age limits, or commit-log capacity, the engine must flush its contents to persistent storage as an immutable file, known as a Sorted String Table (SSTable).

Asynchronous Flushing and Concurrency

To prevent write stalls during disk writes, engines decouple write ingestion from disk flushing through state transitions.

When an active Memtable reaches its threshold:

  1. It is marked as immutable and closed to new incoming writes.
  2. A new, empty Memtable is immediately instantiated to accept subsequent client requests without interruption.
  3. The immutable Memtable is enqueued for a background flush thread pool, which serializes the sorted data and streams it sequentially to disk as an SSTable.

By converting random in-memory mutations into purely sequential disk writes, engines align their I/O profile with the optimal access patterns of modern NVMe and SSD storage.

Backpressure and Write Throttling

If client write rates outpace disk throughput, immutable Memtables will accumulate in RAM faster than background threads can write them to disk. Unchecked, this disparity causes Out-Of-Memory (OOM) crashes or read degradation.

To counter this, wide-column engines employ backpressure mechanisms:

  • Memory Watermarks: High-water marks trigger proactive, asynchronous flushes before buffers reach absolute limits.
  • Request Throttling: If the flush queue exceeds safe thresholds, the engine artificially throttles incoming writes or pauses processing at the coordinator level, forcing client drivers to back off until disk writes catch up.
  • Commit Log Limits: If the disk cannot keep up with flushes, the commit log segments cannot be safely recycled, leading to backpressure applied directly to the write path.

Mitigating I/O Contention with Compaction

Flushing memtables creates an abundance of small SSTables, which degrades read performance. Engines use a continuous background process called compaction to merge multiple SSTables into unified, larger files, discarding deleted data (tombstones) and older versions of modified records.

Because compaction competes with write-buffer flushes for the same storage bandwidth, engines prioritize operations:

  • Flush Priority: Memtable flushes are prioritized over compactions to prevent memory exhaustion.
  • I/O Rate Limiting: Storage engines enforce maximum I/O throughput limits (e.g., limiting compaction throughput in megabytes per second) to preserve enough disk bandwidth for memtable flushes and client reads.
  • Adaptive Compaction Strategies: Strategies like Size-Tiered Compaction (optimized for write-heavy workloads) or Leveled Compaction (optimized for read-heavy workloads) allow administrators to match the system’s I/O profile with available hardware capabilities.

Modern Threading and I/O Architectures

Advanced wide-column implementations optimize flush-to-disk mechanics through non-blocking software architectures. Rather than relying on standard kernel page caches and blocking POSIX calls, modern engines often use thread-per-core designs with direct I/O (AIO) and modern Linux interfaces like io_uring.

This approach bypasses the operating system's buffer cache, allowing the database to accurately track every byte scheduled for disk. By directly managing write queues per core and per physical drive, these engines ensure that flushing data never floods disk controllers, maintaining low latency and predictable write performance at scale.
