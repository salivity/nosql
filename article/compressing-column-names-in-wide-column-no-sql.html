Compressing Column Names in Wide-Column NoSQL

Wide-column NoSQL databases store data in flexible, sparse formats where each cell historically contained a row key, column qualifier, timestamp, and value. While this architecture grants schema flexibility, writing identical column names across millions of physical rows introduces massive storage overhead. This article explains the primary mechanisms wide-column systems—such as Apache Cassandra, Apache HBase, and Google Bigtable—use to eliminate and compress physical column name redundancy, ranging from schema-aware serialization to block-level compression.

Schema-Aware Row Layouts

Early iterations of wide-column engines, such as Cassandra 2.x, treated every row as a loose collection of cells, appending the full string name of the column to every single cell value. Modern engines have largely moved to schema-aware storage layouts.

In modern Cassandra (versions 3.0 and later), the storage engine separates metadata from physical cell storage. The schema definition assigns small internal numerical identifiers (usually a 1- or 2-byte integer) to column names. When rows are serialized to disk, the database writes only these compact IDs or places values in a predefined positional order corresponding to the table's schema. This structural shift eliminates repeated string labels from physical rows entirely.

Prefix and Key Delta Encoding

In systems based on Google Bigtable and Apache HBase, data is stored in sorted file formats like HFiles. Within these files, cells are stored as key-value pairs sorted lexicographically by row key, column family, column qualifier, and timestamp.

Because contiguous cells frequently share identical row keys and column names, these systems use prefix compression (or delta encoding):

  • Prefix Encoding: The storage engine compares each cell key to the preceding key. Instead of repeating identical byte sequences, it stores the length of the matching prefix followed only by the suffix bytes that differ.
  • Diff Encoding (Fast Diff): Used in HBase, this technique tracks the row key, column family, column qualifier, and timestamp independently. If the column qualifier is identical to the previous cell, a single flag indicates a match, bypassing the qualifier bytes completely.

Dictionary Encoding

For column qualifiers that vary across rows but draw from a bounded set of values, dictionary encoding replaces repetitive string names with compact integers. The database builds a dictionary mapping unique column names to short integer codes at the start of each file block or SSTable. The physical records then reference the dictionary key rather than embedding the full text string.

Block-Level Sliding-Window Compression

Physical data files (SSTables or HFiles) are structured into discrete blocks, typically ranging from 4 KB to 64 KB in size. Before these blocks are flushed to disk, they pass through streaming, general-purpose compression algorithms such as LZ4, Snappy, or Zstandard.

Because these algorithms rely on sliding-window byte matching (such as LZ77), any remaining column name redundancy within a single block is compressed automatically. If an identical column name appears multiple times within the block window, subsequent occurrences are replaced with small offset-length references pointing back to the first instance.
