How Document NoSQL Engines Optimize Memory Caching

Document NoSQL engines maximize performance and throughput by keeping frequently accessed documents readily available in RAM, reducing expensive disk I/O operations. This article explores the core architectural strategies these databases use to optimize memory caching, including adaptive cache eviction algorithms, working set management, compressed page storage, index prioritization, and off-heap memory management.

Adaptive Cache Eviction Policies

To ensure memory is reserved for high-value data, document stores rely on advanced eviction algorithms that evaluate both recency and frequency of access. Rather than relying on simple Least Recently Used (LRU) mechanisms—which are susceptible to scan pollution when a batch job scans a large, cold dataset—modern engines employ variants such as:

  • Least Recently Used (2Q / LRU-K): Tracks multiple queues to separate one-off reads from recurring document accesses.
  • Adaptive Replacement Cache (ARC): Dynamically tunes the balance between frequency and recency based on real-time workload behavior.
  • Window TinyLFU (W-TinyLFU): Uses compact frequency sketches (e.g., Count-Min Sketches) to retain frequently read documents while giving newly inserted documents a temporary "admission window" to prove their utility.

Working Set Architecture and In-Memory Tiering

NoSQL engines are built around the concept of the "working set"—the subset of data and indexes actively used during normal business operations. Engines optimize memory through hierarchical tiering:

  1. Process-Level Cache: The database engine’s internal memory manager (such as MongoDB's WiredTiger cache or Couchbase's managed memory) maintains deserialized or partially decoded document objects for low-latency retrieval.
  2. Operating System Page Cache: Documents that fall out of the engine's internal cache often land in the OS file system cache. By avoiding direct I/O for read operations, the engine can pull data from system RAM before resorting to disk reads.

Compression in Memory

To pack more hot documents into limited physical memory, several document databases store pages in compressed formats within their internal caches. Engines divide storage into blocks (typically 4 KB to 64 KB) and compress them using fast algorithms such as Snappy, LZ4, or Zstandard.

This creates a deliberate trade-off: spending minimal CPU cycles to decompress a block is significantly faster than fetching uncompressed data from NVMe or SSD storage. Highly repetitive JSON or BSON schemas benefit substantially from this technique, often achieving a 2x to 4x memory capacity multiplier.

Index-First Prioritization

Document engines prioritize memory allocation for secondary indexes over full document payloads. Because document queries rely on indexes to locate specific documents via B-Trees, LSM-Trees, or hash maps, keeping index nodes in memory ensures fast traversal.

Furthermore, when queries are "covered"—meaning all requested fields reside entirely within the index itself—the engine serves the request directly from the cached index structure without paging the underlying document into memory.

Off-Heap Memory and GC Avoidance

In engines written in managed languages (such as Java, C#, or Go), caching large volumes of JSON documents can trigger severe Garbage Collection (GC) pauses. To counteract this:

  • Off-Heap Allocations: Engines allocate native memory blocks directly via system calls (e.g., malloc or sun.misc.Unsafe in Java), bypassing language runtime heaps.
  • Slab Allocation: Pre-allocated, fixed-size memory chunks (slabs) are assigned to documents of similar sizes. This completely avoids runtime memory fragmentation and minimizes allocation overhead for read-heavy operations.

Write-Behind and Read-Through Caching

To optimize hot documents during concurrent read and write operations, engines employ read-through and write-through/write-behind pipelines.

When a document is updated, the change is applied immediately to the cached version in RAM and recorded sequentially to an append-only write-ahead log (WAL) for durability. Dirty pages are then asynchronously flushed to the persistent storage layer in batches. Subsequent reads hit the updated document in memory immediately, eliminating read delays and amortizing disk write overhead.
