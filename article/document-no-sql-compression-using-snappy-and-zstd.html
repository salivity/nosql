Document NoSQL Compression Using Snappy and Zstd

Document NoSQL databases like MongoDB and Couchbase rely heavily on compression algorithms such as Snappy and Zstandard (Zstd) to minimize storage footprints and reduce disk I/O bottlenecks without crippling CPU throughput. This article explains the underlying mechanics of how document payloads are serialized, grouped, and compressed, highlighting the technical differences between Snappy’s speed-oriented architecture and Zstd’s ratio-optimized entropy encoding.

The Ingestion and Serialization Phase

Before compression occurs, raw data formats like JSON are converted into structured binary representations (such as BSON, FlatBuffers, or custom internal binary layouts). Binary formats standardize data types, establish explicit byte lengths for fields, and eliminate redundant whitespace. This step creates a predictable byte stream, making it significantly easier for pattern-matching compression algorithms to identify repetitive data structures.

Block-Level vs. Document-Level Compression

While some systems allow individual document compression, modern storage engines (such as MongoDB's WiredTiger or RocksDB-backed NoSQL variants) typically perform compression at the block or page level, usually between 4 KB and 64 KB.

Compressing isolated, small documents yields poor compression ratios because the sliding window lacks enough context to find recurring patterns. By packing multiple documents into a single page, the compression algorithm can exploit structural redundancies across different documents—such as identical field names, shared schema definitions, and recurring values.

Snappy: Optimized for Pure Throughput

Snappy, developed by Google, prioritizes execution speed over achieving the highest compression ratio. It does not use entropy encoding (like Huffman coding), which requires computationally expensive bit-level operations.

Instead, Snappy relies on a byte-oriented variant of the LZ77 algorithm:

  1. Hash Table Lookup: As the byte stream is processed, Snappy maintains a small hash table of recent 4-byte sequences to identify repeated substrings within a sliding window.
  2. Back-References: When a duplicate sequence is found, it is replaced with an offset and length pointer (an "element match"). Unmatched sequences are emitted as raw "literals."
  3. Byte Alignment: All emitted tokens are byte-aligned. This allows modern CPUs to read and write without shifting bits, delivering multi-hundred megabyte-per-second compression and gigabyte-per-second decompression speeds per core.

In document stores, Snappy is the default choice for write-heavy, latency-sensitive workloads where CPU cycles are at a premium and disk I/O is fast (e.g., NVMe storage).

Zstandard (Zstd): High Ratios with Adaptive Speed

Zstd, developed by Meta, provides compression ratios approaching gzip with decompression speeds comparable to Snappy. It achieves this balance through a multi-stage pipeline:

  1. FSE (Finite State Entropy): Zstd uses Asymmetric Numeral Systems (tANS) alongside Huffman coding for its entropy stage. FSE allows precise state transitions that encode symbols with fractional bits, providing superior compression density without the heavy computational overhead of traditional arithmetic coding.
  2. Tunable Levels: Zstd offers levels ranging from 1 to 22. Most database engines use levels 1 through 3 for real-time operations, maintaining rapid throughput while beating Snappy’s compression ratio by 10% to 30%.
  3. Dictionary Training: A key advantage of Zstd in document stores is its native dictionary support. Databases can pre-train a static dictionary on the document schema (field names, standard metadata keys). The engine then references this shared dictionary during block compression, allowing even tiny, isolated documents to be compressed efficiently without storing key names redundantly inside every block.

Runtime Memory and I/O Mechanics

During read and write operations, the database engine maintains an in-memory page cache alongside the operating system buffer cache.

  • Writes: Documents accumulate in an uncompressed memory buffer. Once the buffer reaches the block threshold, the storage engine invokes Snappy or Zstd to compress the entire block, adds an integrity checksum (e.g., CRC32), and writes the compressed block sequentially to disk.
  • Reads: When a document is requested, the engine reads the compressed block from disk into memory, decompresses the entire block into the internal cache, and serves the targeted document. Decompression speeds are critical here; if decompression is too slow, read latency spikes regardless of disk speed.

By matching workload requirements to the algorithm—Snappy for low-CPU, high-concurrency ingestion, and Zstd for balanced performance and reduced storage costs—NoSQL engines maintain sub-millisecond document retrieval across massive data volumes.
