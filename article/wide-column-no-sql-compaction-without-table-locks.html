Wide-Column NoSQL Compaction Without Table Locks

Wide-column NoSQL databases like Apache Cassandra, ScyllaDB, and Apache HBase achieve lock-free background compaction by leveraging Log-Structured Merge-tree (LSM-tree) architectures and immutable data files. Instead of modifying existing data in place—which would require coarse-grained locking—these systems write merged and purged data into entirely new files while background threads handle file management. This ensures that client read and write operations continue uninterrupted with high throughput and low latency.

The Role of Immutable SSTables

The foundation of non-blocking compaction is immutability. In an LSM-tree-based engine, incoming writes are first appended to an on-disk commit log for durability and written to an in-memory buffer called a Memtable. Once the Memtable fills up, it flushes to disk as an immutable Sorted String Table (SSTable).

Because SSTables are read-only and never modified in place, reads and background operations do not compete for file-level write locks. When updates or deletes occur, the database simply writes a newer timestamped version or a deletion marker known as a tombstone.

The Compaction Execution Flow

Automatic background compaction operates via dedicated background worker threads separate from client request coordinators. The process follows these steps:

  1. Selection: Compaction strategies (such as Size-Tiered, Leveled, or Time-Window) continuously monitor file metrics and select a candidate set of overlapping SSTables.
  2. Merging and Purging: Background workers stream data concurrently from the candidate SSTables, performing a k-way merge sort. During this pass, the system keeps only the latest timestamped version of each cell, discards older overwritten variants, and removes expired tombstones.
  3. Writing New SSTables: The consolidated data is streamed into brand new, temporary SSTables on disk. Existing SSTables remain completely untouched and active during this phase.

Handling Reads and Writes Concurrently

Client operations run concurrently with compaction without requiring table locks:

  • Writes: Client writes interact strictly with the in-memory Memtables and append-only commit logs. They never touch SSTables directly, making writes completely decoupled from compaction.
  • Reads: Read operations continue querying the active Memtables and the existing candidate SSTables. Even though those candidate SSTables are being read by compaction workers, multiple reader threads can scan immutable files simultaneously without contention.

Atomic Metadata Swapping

Once the new SSTables are fully written and synced to disk via fsync, the engine must replace the old files. It achieves this transition without locking via an atomic metadata swap.

The database updates its internal file manifest (or in-memory file reference list) using atomic pointers. In a single atomic operation, the new SSTables are marked as active for new read queries, and the old candidate SSTables are marked for removal. Any in-flight read operations that were already scanning the old SSTables continue reading them safely via existing file descriptors. Once those active queries complete and reference counts drop to zero, background cleanup routines safely unlink and delete the old files from the filesystem.

Resource Throttling and Isolation

To prevent background compaction from starving foreground reads and writes of disk I/O and CPU, wide-column engines implement strict throttling mechanisms. Compaction tasks are allocated configurable throughput limits (often measured in megabytes per second) and run on low-priority worker threads. Advanced engines like ScyllaDB use user-space scheduling and asynchronous I/O to dynamically balance compaction work against foreground request latency, ensuring the database remains responsive under heavy workloads.
