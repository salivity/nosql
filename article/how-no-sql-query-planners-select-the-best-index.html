How NoSQL Query Planners Select the Best Index

Document-based NoSQL databases rely on intelligent query planners to execute read operations with minimal latency and resource consumption. When an application queries a collection, the query planner assesses the query structure, filters through available indexes to identify viable candidates, and determines the most cost-effective path to fetch the requested documents. This article breaks down the index selection lifecycle in modern document stores, exploring candidate filtering, cost estimation versus empirical execution races, covered query evaluation, and execution plan caching.

1. Identifying Candidate Indexes

The query planner begins by analyzing the query predicate, which includes filter conditions, sort orders, and projected fields. It extracts the referenced attributes and compares them against the database's metadata catalog to find compatible indexes.

An index is flagged as a candidate if it aligns with the query criteria:

  • Equality and Range Matching: Single-field or compound indexes containing the fields used in $eq, $gt, $in, or other filter operators.
  • Compound Index Prefix Rules: For compound indexes, the planner checks whether the query fields match the leading attributes of the index key pattern (left-prefix rule).
  • Sort Compatibility: The planner checks whether an index can satisfy an ORDER BY or sort operation directly via its natural traversal order, eliminating the need for an expensive in-memory sort.

2. Eliminating Incompatible Candidates

Once candidate indexes are identified, the planner prunes those that cannot satisfy the query requirements or would perform worse than a primary scan. For instance, if a query filters on status and created_at, an index solely covering user_id is immediately discarded. Similarly, if an index requires an in-memory sort when a memory limit is constrained, and another candidate index natively satisfies the sort order, priority shifts to the sorting-compatible index.

3. Evaluating Plan Efficiency

Different document stores resolve the optimal index using either statistical cost models or empirical trial executions:

Empirical Plan Racing (e.g., MongoDB)

Instead of relying strictly on static statistics, some document engines run a competition among candidate plans.

  • The planner generates candidate execution plans for the top candidate indexes, alongside a collection scan if applicable.
  • It executes these candidate plans simultaneously in a short trial phase, advancing each plan by a fixed number of operations or "work units."
  • The winning plan is the one that produces the required results first, examines the fewest index keys, or performs the fewest document fetches from disk.

Cost-Based Optimization (CBO) (e.g., Couchbase N1QL)

Other engines use statistical cost formulas similar to relational databases:

  • The planner inspects data distribution statistics, such as histograms, cardinality, and total key counts.
  • It estimates the selectivity of the query predicates: a highly selective index that filters out 99% of documents is assigned a lower cost score than a low-selectivity index.
  • Estimated I/O operations, CPU cycles, and memory consumption are summed to assign a numeric cost value to each candidate. The index with the lowest predicted cost is chosen.

4. Prioritizing Covered Queries

A significant factor in index selection is whether an index can produce a "covered query." A query is covered when all fields requested in the filter, sort, and projection exist directly within the index leaves. In this scenario, the database engine reads data directly from the index without dereferencing or fetching the underlying document from storage. Query planners strongly favor covered indexes because bypassing document retrieval drastically reduces random disk I/O and cache thrashing.

5. Plan Caching and Invalidation

Evaluating indexes for every single incoming operation introduces unacceptable latency. To prevent this overhead, document query planners implement plan caching:

  • Query Fingerprinting: The planner abstracts the query into a "query shape" by replacing specific literal values with placeholders while preserving the targeted fields, operators, and sort directives.
  • Cache Storage: The winning index plan is stored in an in-memory cache mapped to that query shape. Subsequent queries matching the same shape bypass the selection phase and use the cached plan immediately.
  • Invalidation Triggers: Cached plans are invalidated and re-evaluated when the collection structure changes (e.g., an index is added or dropped), when a plan fails to return data efficiently (degradation), or when a collection undergoes massive write activity that alters data distribution.
