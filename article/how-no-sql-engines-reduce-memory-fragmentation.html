How NoSQL Engines Reduce Memory Fragmentation

NoSQL databases process high volumes of dynamic, concurrent read and write operations that frequently allocate and deallocate variable-sized data blocks. Without specialized memory management, this behavior causes severe memory fragmentation, leading to wasted RAM, degraded cache locality, and unpredictable latency spikes. To mitigate these risks, NoSQL engines employ modern alternative memory allocators, custom slab and arena allocation schemes, active background defragmentation, and off-heap memory architectures. This article examines the core mechanisms NoSQL engines rely on to control memory fragmentation and maintain predictable throughput.

Replacing Default Allocators with jemalloc and TCMalloc

Standard system allocators, such as the default GNU C Library malloc, are designed for general-purpose workloads and often suffer from severe external fragmentation under concurrent, multi-threaded workloads. Most NoSQL systems (such as Redis, Aerospike, and MongoDB's WiredTiger engine) bypass the default glibc allocator in favor of jemalloc or TCMalloc (Thread-Caching Malloc).

These advanced allocators reduce fragmentation through two primary techniques:

  • Fine-Grained Size Classes: Instead of allocating arbitrary byte sizes directly from the OS, jemalloc and TCMalloc categorize requests into dozens of predetermined size classes (bins). By rounding requests up to standard sizes, the allocator reuses free slots consistently, virtually eliminating small gaps between allocated blocks.
  • Thread-Specific Caching: Each thread maintains an independent cache for small allocations. This isolates thread memory operations, reduces global lock contention, and ensures that memory freed by a thread is quickly reused for subsequent operations of the same size before dirtying new operating system pages.

Slab Allocation for Fixed-Size Data Structures

For workloads characterized by high churn of uniform objects, NoSQL engines implement slab allocation. First popularized in kernel architectures and caching engines like Memcached, slab allocation groups memory into large contiguous blocks called "slabs."

Each slab is sliced into equal-sized slots tailored to a specific data size class. When an engine inserts a new record:

  1. It identifies the slab class that best fits the record's payload.
  2. It assigns an open slot within that specific slab.
  3. Upon deletion, the slot is marked as free within its original slab, ready to be immediately overwritten.

Because slots within a slab never change size, external fragmentation is structurally eliminated. Engines balance this against internal fragmentation (the unused padding within a slot) by maintaining finely spaced slab classes.

Arena and Region-Based Allocation

Log-Structured Merge-tree (LSM-tree) based engines, such as RocksDB and Apache Cassandra, heavily utilize arena-based (or region-based) allocators to manage write buffers (MemTables).

Instead of allocating and freeing individual key-value pairs independently:

  • The engine allocates large, contiguous memory arenas (typically several megabytes in size).
  • Writes append sequentially into the arena buffer, maximizing memory density and CPU cache efficiency.
  • When the MemTable is flushed to disk as an immutable SSTable, the entire arena is reclaimed in a single operation.

Freeing entire memory regions simultaneously prevents the formation of isolated, unallocated holes that typically occur when records are deleted sporadically.

Active Background Defragmentation

Even with optimized allocation strategies, long-running in-memory databases can develop fragmentation over time as keys expire or mutate. Systems like Redis feature built-in active defragmentation capabilities that operate at runtime without requiring restarts.

Active defragmentation works by:

  1. Introspecting Memory Pages: The engine queries allocator APIs (such as jemalloc's control interface) to detect physical memory pages with high ratios of unused space to allocated data.
  2. Copy-and-Reallocate: The engine scans keys residing in fragmented pages, allocates contiguous new copies in well-utilized pages, updates pointer references, and releases the original memory.
  3. Adaptive Throttling: The defragmentation routine monitors CPU overhead, scaling its execution up during idle periods and throttling down during high-traffic spikes to avoid impacting query latency.

Off-Heap Memory and Zero-Copy I/O

For NoSQL systems running on managed runtimes like the Java Virtual Machine (such as Apache Cassandra, Apache HBase, and Hazelcast), garbage collection (GC) fragmentation poses a major operational hazard. JVM heap fragmentation triggers expensive Stop-The-World compaction events.

To circumvent this, these engines allocate long-lived structures—such as read caches, bloom filters, and buffer pools—directly off-heap using APIs like Java’s Unsafe or ByteBuffer.allocateDirect(). Bypassing the JVM heap allows the engine to handle memory allocations natively via direct C-level calls or custom chunk-based pooling mechanisms, ensuring that long-lived database caches do not fragment the application runtime.
