NoSQL Partial Updates on Nested Document Arrays

This article explores how document-oriented NoSQL databases process partial updates on arrays containing nested subdocuments. Modern document stores avoid the costly anti-pattern of rewriting entire documents by using dot notation, path expressions, positional operators, and engine-level atomic modifications. Below is a breakdown of how these engines identify target elements, apply granular changes, manage internal storage mutations, and ensure concurrency control during partial updates.

Targeted Path Traversal and Positional Operators

Document databases such as MongoDB, Couchbase, and Amazon DynamoDB locate specific nested array items using structured path expressions. Instead of passing the entire array back to the client, the client specifies a query condition alongside an update operation.

Engines rely on positional operators to update matched elements:

  • First Matched Element ($): Identifies the first array element that meets the query criteria and applies changes only to specified keys inside that subdocument.
  • All Matched Elements ($[<identifier>]): Evaluates an array filter expression against every subdocument in the array, applying modifications to all elements that satisfy the condition.
  • All Elements ($[]): Applies the partial update uniformly to every nested document in the array.

Atomic Operation Execution at the Engine Level

When a database receives a partial update command targeting a nested array, it executes the operation atomically at the document level:

  1. In-Memory Traversal: The storage engine reads the document into memory and parses its binary format (such as BSON in MongoDB or Ion in DynamoDB).
  2. Expression Evaluation: The engine walks the document’s abstract syntax tree to find the array, iterates over its entries, and evaluates the update filter conditions against the nested fields.
  3. In-Place Field Patching: If the update only changes scalar values or adds fields without altering the array's order, the engine modifies the specific byte offset in the internal document representation.
  4. Log Ahead/Journaling: The engine writes the delta change to the Write-Ahead Log (WAL) or journal, ensuring durability before marking the operation complete.

Array Mutation Mechanics: Additions and Removals

Modifying the structure of a nested array requires different handling than changing existing values:

  • Push Operations: Appending an element to a nested array checks whether the document has pre-allocated contiguous space. If space permits, the engine appends the subdocument. If the allocated boundary is exceeded, the storage engine must reallocate and move the document elsewhere on disk, updating internal index pointers.
  • Pull and Filter Removals: Deleting a nested subdocument causes the remaining elements in the array to shift left. Engines rewrite the array payload and mark the newly freed space as reusable within the document's allocation block.

Concurrency and Document-Level Locking

Document NoSQL engines generally enforce atomicity and isolation at the single-document level:

  • Pessimistic/Row-Level Locks: Engines like WiredTiger lock the specific document while evaluating array filters and writing modifications. Concurrent updates to different parts of the same array are queued, preventing lost updates or race conditions.
  • Optimistic Concurrency Control (OCC): Engines like DynamoDB evaluate conditional expressions (e.g., matching a version field or specific array state). If another transaction modifies the nested array between the read and write stages, the update rejects with a transaction conflict, requiring the client to retry.
