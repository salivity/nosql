Time-Series NoSQL Database Compression Explained

Time-series NoSQL databases process massive volumes of sequential data that arrive at regular intervals and often fluctuate within narrow numeric bands. To prevent runaway storage costs and maintain fast query execution, these databases bypass general-purpose compression algorithms in favor of specialized, lightweight encoding techniques. By combining Delta-of-Delta encoding for predictable timestamps with XOR-based floating-point compression and run-length encoding for metrics, time-series engines systematically strip out redundancy at the bit level before archiving data to disk.

Compressing Repetitive Timestamps

Timestamps are 64-bit Unix epoch values that, without compression, consume vast amounts of memory. However, time-series data is typically collected at steady cadences, such as once every second, minute, or hour. Databases leverage this predictability using two primary mathematical transformations:

  • Delta Encoding: Instead of saving an absolute timestamp (e.g., 1710000000, 1710000060, 1710000120), the engine computes the difference between consecutive values. If metrics are polled once per minute, the stored sequence becomes relative increments (60, 60, 60), which drastically reduces the integer magnitudes.
  • Delta-of-Delta Encoding: Standardized by Facebook’s Gorilla time-series architecture, this technique calculates the difference between consecutive deltas (\(D_n = (t_n - t_{n-1}) - (t_{n-1} - t_{n-2})\)). When measurements occur at perfectly regular intervals, the delta-of-delta is zero. The database can represent a zero value using a single binary bit (0). When network latency or clock skew causes jitter, the system outputs a non-zero marker followed by variable-length bit-packing to record only the magnitude of the drift.

Compressing Metric Values

Metrics present different patterns than timestamps, alternating between completely static measurements, gradual variations, and sudden spikes. Specialized algorithms target these specific behaviors depending on whether the data is floating-point or integer-based.

  • XOR Floating-Point Compression: Standard IEEE 754 floating-point numbers often share identical exponent and mantissa bits when consecutive measurements deviate only slightly. The engine compares the current floating-point value to the preceding one using a bitwise XOR operation. If the values are identical, the result is zero, which is stored as a single bit. If they vary, the system records only the non-zero "meaningful bits," discarding redundant leading and trailing zeros.
  • Run-Length Encoding (RLE): Ideal for operational statuses, discrete state flags, or counters that remain static for long periods. Instead of storing repeated entries individually (e.g., [Online, Online, Online, Online]), RLE stores the distinct value paired with a frequency count (e.g., Online x 4).
  • Frame-of-Reference (FoR) and Bit-Packing: Used primarily for integer measurements. The engine identifies the minimum value in a given block as the "frame of reference" and stores subsequent numbers as small offsets relative to that baseline. The engine then calculates the maximum bit width needed to store the largest offset in the block and packs the values tightly, shedding the unused high-order bits typically reserved by 32-bit or 64-bit systems.

Columnar Layout and Secondary Compression

To maximize the efficiency of these algorithms, time-series databases organize records into columnar blocks rather than traditional row-oriented tuples. Timestamps are grouped together in one continuous array, while metric values are isolated in another. This guarantees that similar data types and patterns are processed adjacent to one another.

Once the specialized algorithms (Delta-of-Delta, XOR, RLE) reduce the raw data into tight bit streams, the database frequently applies a secondary, general-purpose byte-level compression pass—such as Zstandard (zstd) or Snappy. Because the underlying data has already been linearized and stripped of entropy, this secondary pass achieves high compression ratios with minimal CPU overhead.
