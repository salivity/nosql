How Key-Value NoSQL Engines Handle OOM Errors

Key-value NoSQL engines maintain memory safety during out-of-memory (OOM) conditions by combining proactive resource tracking, defensive memory allocation, request admission control, and controlled data shedding. Rather than relying on the operating system’s default memory management—which often terminates processes abruptly via the kernel OOM killer—these databases use embedded limits, custom allocators, and deterministic degradation strategies to prevent crashes, memory leaks, and state corruption.

Custom Memory Allocators and Precise Accounting

Standard runtime allocators like glibc malloc often struggle with fragmentation and lack fine-grained introspection. Key-value stores such as Redis and RocksDB frequently integrate specialized allocators like jemalloc or tcmalloc.

These allocators provide internal hooks to track total allocated bytes, active resident set size (RSS), and fragmentation metadata in real time. By continuously checking their active footprint against configured memory limits, engines detect memory exhaustion before an allocation request triggers an operating system panic or returns a null pointer that could cause a segmentation fault.

Proactive Admission Control and Error Propagation

When memory crosses a predefined safety threshold, the storage engine switches to a defensive operating mode:

  • Write Rejection: The engine immediately stops accepting state-mutating requests (such as SET, PUT, or append operations) and returns clear application-level errors (for example, Redis's OOM command not allowed).
  • Read and Delete Availability: Read commands (GET) and removal operations (DEL) remain functional. This ensures clients can still retrieve critical data or explicitly delete keys to alleviate memory pressure.
  • Non-allocating Error Paths: Error paths are designed to avoid dynamic allocations entirely. If generating an error message requires allocating heap memory, the engine could crash; therefore, static pre-allocated error buffers are returned to the client.

Automated Eviction and Expiration

To prevent reaching absolute capacity, key-value engines implement configurable eviction policies that execute synchronously or via low-priority background threads:

  • Volatile and All-Keys LRU/LFU: The engine removes the Least Recently Used (LRU) or Least Frequently Used (LFU) keys to reclaim memory.
  • TTL Sampling: Expired keys are identified and deleted either lazily (upon access) or actively via background sweeps to free chunks of dead memory.
  • Memory Defragmentation: When high fragmentation prevents contiguous allocations despite available logical memory, the engine incrementally reallocates data into continuous pages without blocking the primary execution loop.

Disk-Spilling and MemTable Flushing

Log-structured merge-tree (LSM) engines like RocksDB or Pebble manage memory safety by offloading in-memory state to non-volatile storage:

  • Write Buffers (MemTables): Incoming writes are buffered in memory. When a buffer reaches its size threshold, it becomes read-only and a background thread flushes it to disk as an immutable SSTable file.
  • Write Stalls: If background flushing cannot keep up with high write throughput and memory approaches critical limits, the engine deliberately stalls or throttles incoming writes (backpressure) rather than allowing memory usage to climb indefinitely.

Process Isolation and Kernel Mitigation

At the operating system level, production-grade key-value deployments adjust process priority using Linux's oom_score_adj. By assigning a lower score to the primary database process, administrators signal to the kernel that other ancillary processes should be terminated first during system-wide memory starvation.

Simultaneously, the engine ensures that memory mappings (such as mmap references used for caching index blocks) are handled with bounds checking and system call validation to intercept ENOMEM codes cleanly, preserving process integrity and safeguarding persistent storage from partial writes.
