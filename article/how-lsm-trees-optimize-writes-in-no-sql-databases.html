How LSM-Trees Optimize Writes in NoSQL Databases

Log-Structured Merge-trees (LSM-trees) are a foundational data structure powering high-throughput write workloads in modern NoSQL databases like Apache Cassandra, ScyllaDB, and RocksDB. This article explores how LSM-trees optimize write performance by replacing expensive random disk writes with fast sequential writes, detailing the roles of Write-Ahead Logs, in-memory MemTables, immutable Sorted String Tables (SSTables), and background compaction.

The Bottleneck of Traditional B-Trees

Traditional relational databases commonly rely on B-trees or B+ trees to manage data. While B-trees excel at fast read operations, they require in-place updates. Modifying a record means locating its specific page on disk and rewriting it. Under write-heavy workloads, this results in continuous random disk input/output (I/O). Because random I/O requires high physical overhead—even on Solid State Drives (SSDs)—it drastically limits write throughput and causes high write amplification.

The LSM-Tree Write Path

LSM-trees circumvent random disk access by decoupling the ingestion of data from its long-term organization on disk. When a write request arrives, it follows a multi-stage path designed to maximize sequential I/O:

  1. Write-Ahead Log (WAL): The write is immediately appended to an on-disk commit log. Because this write is strictly append-only, the disk performs a fast sequential write, ensuring data durability in the event of a sudden crash or power loss.
  2. MemTable: Concurrently, the record is inserted into an in-memory buffer called the MemTable. The MemTable is typically implemented as a sorted data structure, such as a SkipList or Red-Black Tree. Once the data resides in the MemTable and the WAL, the database acknowledges the write as successful to the client. This entire process takes microseconds.

Flushing to SSTables

As write traffic continues, the MemTable eventually reaches its allocated memory limit. Instead of updating data in place on disk, the database performs the following actions:

  • The active MemTable becomes immutable, and a new empty MemTable is allocated to continue receiving client writes without interruption.
  • A background thread flushes the immutable MemTable to disk as a Sorted String Table (SSTable).
  • Because the keys are already sorted in memory, the flush writes data to the disk in a single, continuous, sequential stream.
  • SSTables are entirely immutable; once written to disk, they are never modified or rewritten in place. Deletions are handled by writing a marker called a "tombstone" rather than physically deleting data immediately.

Background Compaction

Because data is written out as multiple immutable SSTables over time, older SSTables can contain outdated versions of rows or deleted records marked with tombstones. LSM-trees resolve this through a continuous background process called compaction.

Compaction merges multiple SSTables into a new, single SSTable using a merge-sort algorithm. During this process, the engine:

  • Resolves duplicate keys by keeping only the most recent version based on timestamps.
  • Purges records marked by tombstones.
  • Removes obsolete SSTables from disk, reclaiming storage.

Because compaction runs asynchronously in the background, it shields incoming write requests from the latency of reorganizing data.

Why LSM-Trees Maximize Write Performance

LSM-trees maximize write throughput through three primary design advantages:

  • Elimination of Random Writes: All client-facing writes occur either in memory (MemTable) or sequentially on disk (WAL and SSTable flushes), matching the physical strengths of modern storage hardware.
  • Deferred Work: Expensive tasks, such as deduplication and space reclamation, are pushed to background compaction routines rather than executed on the critical write path.
  • Lock-Free Concurrency: Because SSTables are immutable, incoming writes do not need to lock disk pages to prevent dirty reads or conflicts, drastically increasing concurrency.
