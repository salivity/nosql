Wide-Column NoSQL Batch Updates Without Locking

Wide-column NoSQL databases, such as Apache Cassandra and ScyllaDB, handle long-running batch updates without traditional lock contention by relying on append-only architectures, Log-Structured Merge-trees (LSM-trees), and timestamp-based concurrency models. Instead of locking rows or tables to overwrite existing data in place, these systems treat updates as new, immutable writes. This architectural choice decouples read and write operations, allowing sustained, high-throughput batch modifications without causing database bottlenecks or deadlocks.

Log-Structured Merge-Trees and Append-Only Writes

Traditional relational databases update data in place on disk, requiring row- or table-level locks to prevent concurrent processes from reading or writing partially modified states. Wide-column stores avoid in-place mutations altogether by using an append-only write path powered by LSM-trees.

When a batch update arrives at a node:

  1. It is sequentially appended to an on-disk write-ahead log (such as the CommitLog) for crash recovery. Sequential disk access requires no index locking.
  2. It is concurrently written to an in-memory sorted structure known as a MemTable.

Because writes only append data to memory and sequential logs, the database does not need to verify or lock the physical location of existing data. The write operation completes as soon as it resides in the MemTable and the log, minimizing transaction duration from seconds to microseconds.

Timestamp Ordering and Last-Write-Wins (LWW)

Rather than using pessimistic locking to manage concurrent updates to the same record, wide-column engines use cell-level timestamps to implement optimistic concurrency resolution, commonly known as Last-Write-Wins (LWW).

Each column updated within a batch is stamped with a microsecond-precision coordinator or client timestamp. If a long-running batch modifies a column that is simultaneously targeted by another process, both updates are written without blocking. The database defers conflict resolution until read time or background maintenance: whichever write has the latest timestamp is considered the authoritative version.

Asynchronous Compaction

The physical merging of multiple updates to the same cell occurs asynchronously during a process called compaction:

  • When MemTables fill up, they are flushed to disk as immutable SSTables (Sorted String Tables).
  • Over time, background worker threads read multiple SSTables, reconcile duplicate keys using their timestamps, discard older versions or tombstones (deleted records), and write the consolidated result to a new SSTable.
  • Because this process runs completely in the background on immutable files, it operates without halting or locking the active read and write paths.

Partitioning and Batch Distribution

Wide-column databases distribute data horizontally across nodes using consistent hashing based on a partition key. In traditional databases, a batch spanning millions of rows can hold an active transaction lock open across a single server. In contrast, wide-column architectures handle batch processing through distributed partitioning:

  • Token-Aware Routing: Client drivers calculate the partition key hashes of batch items and distribute them directly to the appropriate replica nodes, preventing a single coordinator node from bottlenecking.
  • Independent Atomic Partitions: Long-running batches are typically decomposed into partition-level operations. Since isolation boundaries exist at the partition level, updates to different partitions run in parallel with zero contention.
  • Atomic Batching via Distributed Logs: When atomic guarantees across multiple rows are required (such as logged batches), coordinators write batch metadata to a dedicated distributed batch-log rather than holding live locks on the affected rows. If the coordinator fails mid-operation, other nodes replay the log to guarantee eventual consistency without ever having blocked other client transactions.
