Indexing Dynamic Fields in NoSQL Documents

This article explores how NoSQL document-oriented databases index dynamic fields that cannot be predicted during design time. It outlines the foundational mechanisms modern document stores employ—such as wildcard indexing, inverted indexes, and structural design patterns—to maintain high query performance across polymorphic and arbitrary JSON or BSON data without requiring strict schema definitions.

The Challenge of Dynamic Fields

Traditional relational databases depend on rigid, predefined schemas where each column is statically defined and indexed. Document databases (such as MongoDB, Couchbase, and Amazon DocumentDB) allow polymorphic schemas where different documents within the same collection can feature entirely unique fields, deeply nested objects, and arbitrary key-value pairs. Because database indexes (typically B-Tree or LSM-Tree variants) require a specific key path to extract and sort values, indexing unpredictable paths requires specialized indexing architectures.

Wildcard and Path-Based Indexes

The most common native solution is wildcard indexing. Rather than targeting a fixed field (e.g., user.profile.age), a wildcard index targets an entire document sub-tree or the entire document using path syntax (such as $** in MongoDB).

When a wildcard index is created, the database engine flattens every nested path into a discrete entry during the write operation. For every dynamic field encountered, the storage engine records a tuple containing:

  • The full key path (e.g., attributes.custom_size)
  • The field value (e.g., 42)
  • The document identifier (e.g., _id)

When a query targets a dynamic path, the query planner matches the requested path against the indexed paths stored in the wildcard structure, avoiding a full collection scan.

Inverted Indexes and Dynamic Mapping

Databases built on top of search-engine architectures, such as Elasticsearch or OpenSearch, use dynamic mapping combined with inverted indexes.

When a document with an unknown field arrives:

  1. Dynamic Type Inference: The engine automatically inspects the data type (string, integer, boolean, or date).
  2. Dynamic Mapping Update: The schema definition is updated on the fly in the cluster metadata.
  3. Inverted Index Creation: The term and its location within the document are posted to an inverted index list.

This approach ensures that every dynamic field becomes immediately searchable. However, it can lead to "mapping explosion," where thousands of distinct keys consume excessive memory, typically requiring systems to impose limits on the maximum number of indexed fields.

The Attribute Pattern

When native wildcard indexes are unavailable or incur excessive overhead, dynamic fields are managed at the application level via the Attribute Pattern. Instead of storing dynamic data as arbitrary top-level keys:

{
  "product_id": 101,
  "screen_size": "15-inch",
  "battery_life": "10h"
}

The document is restructured into a deterministic array of key-value pairs:

{
  "product_id": 101,
  "specs": [
    { "k": "screen_size", "v": "15-inch" },
    { "k": "battery_life", "v": "10h" }
  ]
}

By placing a single compound multikey index on specs.k and specs.v, the database indexes all present and future dynamic attributes. The engine treats specs as a fixed schema path, yet it dynamically accommodates any arbitrary attribute without index reconfiguration.

Indexing Generalized Subdocuments

Some systems allow semi-structured subdocuments to be stored as serialized JSON strings or binary dynamic blobs (e.g., PostgreSQL jsonb or Couchbase flexible JSON). These engines utilize Generalized Inverted Indexes (GIN) or hash indexes. The engine reads the raw JSON object, extracts all internal paths and terminal values, and builds an index containing path-value identifiers. Queries testing for path existence (?), key-value equality (@>), or array membership can utilize this single index structure to locate documents quickly.

Performance and Trade-Offs

Indexing dynamic fields introduces distinct engineering trade-offs:

  • Write Amplification: Writing a document with dozens of dynamic fields requires updating dozens of index entries within a wildcard or inverted index, slowing write operations.
  • Storage Footprint: Indexing dynamic paths often consumes significantly more storage than static B-tree indexes because the full attribute path string must be stored alongside the indexed values.
  • Query Optimization Limits: Query optimizers struggle with cardinality estimation on dynamic fields, which can sometimes lead to suboptimal execution plans compared to dedicated, single-field indexes.
