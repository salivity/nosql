How Compaction Optimizes NoSQL Disk Storage

Compaction is an essential background maintenance process used by modern NoSQL databases to manage append-only storage architectures like Log-Structured Merge-trees (LSM-trees). This article explores how compaction functions, why it is critical for reclaiming disk space, and how it directly prevents query degradation by eliminating data fragmentation and reducing read latency.

The Append-Only Write Model

To achieve high write throughput, many NoSQL databases (such as Apache Cassandra, ScyllaDB, and RocksDB) avoid in-place updates. Instead, incoming writes are first placed in an in-memory buffer (MemTable) and an append-only commit log. Once full, the buffer flushes to disk as an immutable data file, commonly called a Sorted String Table (SSTable).

Because files are immutable, updates and deletions do not overwrite existing data. An update simply writes a newer version of a record with a later timestamp, while a deletion writes a marker called a "tombstone." Over time, this design causes:

  • Multiple versions of the same row scattered across dozens or hundreds of files.
  • Wasted disk space occupied by dead or superseded records.
  • High read amplification, forcing read operations to scan multiple files to assemble a single record.

Disk Storage Organization Through Compaction

Compaction resolves the clutter of append-only writes by periodically merging multiple immutable files into newer, unified files.

During this process, the database reads records from multiple input files concurrently in sorted order. It discards older versions of updated rows, permanently drops deleted items whose tombstones have expired, and writes the remaining valid data into a consolidated file. Once the merge finishes, the database atomically unlinks and deletes the old source files.

This reorganizes storage in three vital ways:

  1. Reclaims Space: It purges redundant row mutations and dead data, preventing continuous disk growth.
  2. Sequential Layout: It reorganizes related data contiguously on disk, aligning with OS filesystem blocks for better I/O efficiency.
  3. Reduces File Descriptor Overhead: Consolidating hundreds of small files into fewer, larger structures lowers filesystem metadata tracking and inode usage.

Performance Optimization

Compaction has a direct, positive impact on system performance, particularly during read operations.

Reducing Read Amplification

When reading a key, the database must query multiple SSTables to determine the most recent state of that key. If data is spread across 50 separate files, the database may have to execute 50 disk seeks. Compaction consolidates these fragments into a single file, reducing the number of lookups to as few as one disk access.

Optimizing Auxiliary Data Structures

Databases use Bloom filters and partition indexes to quickly determine if an SSTable contains a requested key without touching the raw data block. Having fewer, compacted files reduces the memory footprint of these indexes and Bloom filters, keeping frequently accessed metadata cached in RAM.

Decreasing Latency Spikes

By maintaining a bounded number of storage files, compaction ensures that tail latency (p99 and p99.9) remains predictable. Without compaction, reads gradually slow down as data accumulates, leading to performance bottlenecks under heavy production loads.

Common Compaction Strategies

Different workloads require different trade-offs between write amplification, read amplification, and storage space. Databases typically allow administrators to configure compaction strategies:

  • Size-Tiered Compaction Strategy (STCS): Merges SSTables of similar sizes. It is efficient for write-heavy workloads, though it requires significant free disk space overhead (often 50%) to execute merges.
  • Leveled Compaction Strategy (LCS): Divides data into hierarchical levels, where each level is ten times larger than the previous one and contains non-overlapping data. This optimizes read performance and minimizes space amplification at the cost of higher write overhead.
  • Time-Window Compaction Strategy (TWCS): Designed for time-series data with TTLs (Time-To-Live). It groups files based on timestamps, allowing entire expired time blocks to be dropped at once with minimal I/O overhead.

Compaction is the engine that makes the high write performance of append-only NoSQL architectures sustainable over time, trading background I/O cycles to guarantee long-term storage efficiency and predictable read speeds.
