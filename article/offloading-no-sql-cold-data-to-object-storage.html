Offloading NoSQL Cold Data to Object Storage

Modern NoSQL databases handle massive volumes of information, but retaining rarely accessed historical data on high-performance NVMe drives is cost-prohibitive. To solve this, database architects implement automated tiering mechanisms that migrate "cold" data to scalable, low-cost cloud object storage such as Amazon S3, Google Cloud Storage, or Azure Blob Storage. This article explores the underlying technical mechanisms—including Log-Structured Merge-tree (LSM) tiering, custom virtual file systems, storage engine compaction hooks, and decoupled compute-storage architectures—that enable seamless cold data offloading without sacrificing data integrity or query access.

LSM-Tree Tiering and Compaction Hooks

Many write-heavy NoSQL databases (such as Apache Cassandra, ScyllaDB, and RocksDB-based systems) use Log-Structured Merge-trees (LSM-trees). LSM-trees organize data into hierarchical levels based on age and update frequency, naturally segregating hot and cold data:

  • Leveled Compaction Migration: As data moves from upper levels (L0, L1) to lower levels (L_max) via background compaction, the database identifies immutable SSTables (Sorted String Tables) containing data older than a predefined threshold.
  • Direct S3 Flushing: Instead of merging these cold SSTables back onto local disks, the compaction worker writes the finalized, immutable blocks directly to object storage using multi-part uploads.
  • Local Metadata Retention: The database retains bloom filters, partition keys, and sparse index offsets on local SSDs. When a read request targets cold data, the engine checks local indexes first and only fetches specific byte ranges via HTTP range requests rather than downloading the entire file.

Virtual File System (VFS) Abstraction Layers

Rather than rewriting database internals, several engines insert an abstraction layer between the database storage engine and the underlying operating system file system:

  • Filesystem Interception: Engines like RocksDB use custom implementations of storage interfaces (such as RocksDB’s Env or FileSystem API).
  • Transparent Routing: The interface intercepts POSIX file calls (read, write). Active files (write-ahead logs, memtable flushes) write to local POSIX storage, while closed, immutable data blocks are assigned an S3 URI.
  • Block Caching: The VFS maintains a local LRU (Least Recently Used) cache for cold blocks fetched from object storage, amortizing network latency for repeated reads.

Decoupled Compute and Distributed Storage Layers

Cloud-native NoSQL offerings separate compute nodes from persistence entirely:

  • Log-Centric Persistence: All writes are committed to a fast, distributed Write-Ahead Log (WAL) or durable memory layer.
  • Segment Packaging: Once data reaches a certain age or size, background worker daemons aggregate log segments into read-optimized columnar formats (such as Apache Parquet or proprietary columnar segments).
  • Direct Offloading: These segments are pushed to object storage, and the local state is purged. The primary compute node only retains cluster topology maps and high-level routing metadata.

Time-to-Live (TTL) and Policy-Driven Archival Pipelines

For document and key-value stores (like MongoDB or Couchbase), tiering is often handled through asynchronous data lifecycle policies:

  • Change Stream Triggers: Internal listeners track record age based on timestamps or TTL indexes.
  • Batch Extraction and Conversion: When documents qualify as cold, an automated pipeline batches the JSON/BSON records, compresses them (e.g., using Snappy or Zstandard), and writes them to cloud buckets partitioned by date or tenant ID.
  • Federated Query Engines: The database engine maintains a unified catalog. When an application queries a historical partition, the query planner delegates the execution to a federated engine capable of executing pushdown predicates against the object store files, stitching the cold results together with hot, local operational data.
