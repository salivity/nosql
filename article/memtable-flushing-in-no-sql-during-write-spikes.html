Memtable Flushing in NoSQL During Write Spikes

Wide-column NoSQL databases like Apache Cassandra and ScyllaDB rely on Log-Structured Merge-tree (LSM-tree) architectures to absorb massive write throughput. During sudden write spikes, these engines maintain low-latency writes by buffering data in memory within structures called memtables while logging them sequentially to disk in a CommitLog. When write volumes threaten to exhaust memory, the database rapidly transitions active memtables into immutable states, queues them for sequential disk serialization as Sorted String Tables (SSTables), and uses adaptive backpressure to throttle incoming traffic if disk I/O falls behind.

The Role of Memtables in LSM-Tree Writes

When a write operation reaches a wide-column store node, it executes two steps:

  1. It appends the mutation to a Write-Ahead Log (CommitLog) on disk for durability.
  2. It writes the mutation to an in-memory sorted structure known as a memtable.

Because both the CommitLog append and the memtable write occur sequentially in memory and on disk, writes execute with sub-millisecond latency. However, because system RAM is finite, memtables must periodically flush their contents to persistent storage as immutable SSTables.

Flush Triggers During Write Spikes

Engines monitor several thresholds to decide when to trigger a flush:

  • Capacity Thresholds: When an individual memtable reaches a predefined size limit (typically configured via heap or off-heap allocations).
  • Global Memory Pressure: When total memory allocated across all active memtables exceeds safe limits, triggering the flush of the largest memtables first to prevent Out-Of-Memory (OOM) errors.
  • CommitLog Saturation: If the sequential write log approaches its segment size limits, the engine must flush older memtables to allow older CommitLog segments to be safely deleted or recycled.

The Flushing Mechanism Under Load

When a write spike triggers a flush, the database executes an asynchronous pipeline designed to keep the write path unblocked:

  1. Memtable Freezing: The active memtable is immediately marked as immutable ("frozen"). Concurrently, the engine instantiates a clean, mutable memtable to accept new incoming writes without interruption.
  2. Handoff to Flush Queues: The frozen memtable is handed off to an internal flush queue managed by a dedicated thread pool.
  3. Sequential I/O Serialization: Flush worker threads iterate through the sorted data in the frozen memtable, serializing it into an immutable SSTable on disk. Because the in-memory data is already sorted, the disk write is entirely sequential, maximizing disk throughput.
  4. CommitLog Truncation and Indexing: Once the SSTable is written, the database updates its partition index, bloom filters, and summary files, then releases the frozen memtable's memory back to the operating system or heap. The corresponding sections in the CommitLog are flagged for reclamation.

Mitigating I/O Bottlenecks and Compaction Contention

Under severe write spikes, flush operations must compete with compaction processes for storage bandwidth. To prevent flushes from stalling, modern engines apply specific prioritization rules:

  • I/O Prioritization: Engines prioritize memtable flushes over background compactions. Because delayed flushes risk filling up system RAM, compaction tasks are paused, throttled, or assigned to lower-priority I/O classes.
  • Off-Heap Storage: Modern implementations store memtables partially or entirely off-heap. This avoids excessive Java Virtual Machine (JVM) garbage collection pauses when memory churn accelerates during spikes.

Backpressure and Flow Control

If the disk subsystem cannot write SSTables as fast as incoming writes generate them, the system activates defensive backpressure mechanisms:

  • Thread Pool Saturation: If the flush queue exceeds capacity, the database blocks new write operations from allocating further memtables.
  • Client Throttling: Incoming write requests are stalled at the coordinator or transport layer. Clients experience increased latency, preventing the cluster nodes from crashing due to memory exhaustion.
  • Drop Policies: In extreme scenarios where native backpressure fails to slow down write volume, coordinators may shed load by dropping timed-out requests or rejecting connections with OverloadedException errors until the flush queue drains.
