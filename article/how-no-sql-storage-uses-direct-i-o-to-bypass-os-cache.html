How NoSQL Storage Uses Direct I/O to Bypass OS Cache

This article explores how high-performance NoSQL storage engines use Direct I/O to circumvent the operating system page cache. By bypassing the kernel's intermediate caching layer, databases eliminate the performance penalties associated with double buffering, CPU-intensive memory copies, and unpredictable kernel-level page evictions. The following sections break down the mechanics of the standard I/O path, the principles of Direct I/O, and the architectural benefits it offers to database management systems.

The Problem: Standard Buffered I/O and Double Buffering

By default, operating systems handle file read and write operations through a mechanism called buffered I/O. When a database requests a block of data from storage:

  1. The OS kernel reads the data from the storage drive into a kernel memory region known as the page cache.
  2. The kernel then copies this data into the user-space memory buffer allocated by the database process.

For general-purpose applications, this caching layer accelerates repeated reads. However, for specialized NoSQL systems, it introduces severe inefficiencies:

  • Double Buffering: The exact same data block resides both in the OS page cache and in the database’s internal cache (such as an LSM-tree block cache). This roughly halves the amount of usable RAM available for caching on the machine.
  • CPU and Memory Bus Overhead: Copying data from kernel space to user space consumes CPU cycles and saturates memory bandwidth, which creates bottlenecks under heavy read and write workloads.
  • Unpredictable Eviction Policies: The kernel generally employs a generic Least Recently Used (LRU) algorithm to evict pages when memory runs low. The OS does not understand the query patterns, index structures, or compaction cycles of the database, often evicting hot index blocks while retaining transient data.

How Direct I/O Bypasses the Kernel Cache

Direct I/O changes this pipeline by opening storage files with specific operating system flags—most notably O_DIRECT on Linux/POSIX systems or FILE_FLAG_NO_BUFFERING on Windows.

When a database performs reads or writes using Direct I/O, the operating system bypasses the page cache entirely. Instead, the storage controller utilizes Direct Memory Access (DMA) to transfer data directly between the physical storage medium (such as an NVMe SSD) and the database's user-space memory buffers.

To use Direct I/O, storage engines must fulfill strict hardware-level constraints:

  • Memory Alignment: User-space data buffers must be aligned to the memory boundary required by the underlying hardware (typically 4 KB).
  • File Offset Alignment: Read and write offsets within the file must be multiples of the logical block size of the underlying storage device.
  • Transfer Size Alignment: The size of any read or write request must strictly match the sector or block size of the drive.

Architectural Benefits for NoSQL Engines

Bypassing the operating system cache gives modern NoSQL storage engines (such as ScyllaDB, Apache Cassandra using specialized storage engines, and RocksDB under specific configurations) deterministic control over hardware resources.

1. Total Cache Authority

Database engines possess contextual knowledge about their data structures that the kernel lacks. An engine knows whether a read is an index lookup, a point read, a large analytical scan, or an internal background compaction. By bypassing the OS cache, the database can implement custom cache eviction algorithms (such as 2Q, TinyLFU, or W-TinyLFU) tailored to its query workload.

2. Elimination of High Tail Latencies

Standard page cache writebacks often cause latency spikes. When the kernel's dirty memory ratio exceeds configured thresholds, the OS forces dirty pages to disk, pausing or slowing application writes. Direct I/O decouples database performance from background kernel flushes, resulting in predictable p99 and p99.9 latency metrics.

3. Optimized Asynchronous I/O Execution

Direct I/O is rarely used in isolation; it is typically paired with asynchronous I/O frameworks like Linux's io_uring or libaio. Because buffered I/O can block threads even when called asynchronously (if metadata needs updating or memory allocation blocks), Direct I/O provides true, non-blocking asynchronous execution. Systems based on thread-per-core architectures issue thousands of concurrent I/O operations directly to NVMe queues without incurring context-switching overhead.

4. Predictable Background Compactions

In Log-Structured Merge-tree (LSM) engines, background compaction processes read large volumes of Sorted String Tables (SSTables) and write newly merged files. If these bulk reads and writes passed through the OS page cache, they would flush critical, frequently accessed read caches. Using Direct I/O for compaction operations guarantees that routine maintenance tasks do not degrade active client query performance.
