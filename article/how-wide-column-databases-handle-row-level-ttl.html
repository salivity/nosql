How Wide-Column Databases Handle Row-Level TTL

This article examines how distributed wide-column NoSQL stores, such as Apache Cassandra and ScyllaDB, manage row-level Time-To-Live (TTL) expiration across petabyte-scale datasets. It explores the mechanics of attaching expiration metadata to storage cells, the process of lazy deletion via read-time filtering, the lifecycle of tombstones, and how background compaction strategies reclaim physical disk space without degrading cluster performance.

Metadata-Driven TTL Assignment

Wide-column stores implement row-level TTL not by scheduling background delete tasks, but by appending metadata directly to the data payload at write time. When a write occurs with a defined TTL:

  1. The database captures the server-side coordinate timestamp (the write time) and calculates the exact epoch expiration time.
  2. The data is written to an in-memory table (Memtable) and appended to the commit log with this metadata embedded at the row or cell level.
  3. When the Memtable flushes to disk, the expiration timestamp is immutably stored within the resulting Sorted String Table (SSTable) file alongside the data and min/max timestamp statistics.

Because writes in Log-Structured Merge-tree (LSM-tree) architectures are append-only, the database never modifies existing on-disk structures to apply or count down a TTL.

Lazy Expiration and Read-Time Filtering

To maintain high throughput on massive datasets, wide-column engines do not scan storage to find expired records. Instead, they use a passive, "lazy" deletion mechanism during read operations:

  • Epoch Comparison: When a client queries a row, the storage engine reads the embedded expiration timestamp from the SSTable or Memtable.
  • Filter on Read: If the current system time exceeds the expiration timestamp, the engine ignores the row, treating it as if it does not exist.
  • Zero Overhead on Idle Data: Data that is never read consumes zero CPU or I/O cycles for expiration checks while resting on disk.

Virtual Tombstones and Compaction

Physical disk space recovery happens asynchronously through SSTable compaction. While explicit deletes in wide-column databases generate "tombstones" (markers indicating a record was deleted), TTL-expired records are often handled as implicit or "virtual" tombstones.

  1. Compaction Discovery: During minor or major compactions, the database reads multiple SSTables and merges them into new ones. During this merge phase, the compaction executor evaluates the expiration timestamp of each row.
  2. Purging Criteria: An expired row is discarded and omitted from the newly written SSTable only if the expiration age exceeds the configured garbage collection grace period (gc_grace_seconds). This grace period prevents deleted data from re-emerging if a replica was offline when the record expired.
  3. Drop Entire SSTables: If an entire SSTable contains only data where the maximum timestamp plus TTL is older than the current time (and past the grace period), the database drops the entire file from the filesystem immediately, bypassing the expensive read-merge-write compaction cycle.

Optimizing TTL with Time Window Compaction Strategy (TWCS)

Using default compaction strategies like Size-Tiered Compaction Strategy (STCS) or Leveled Compaction Strategy (LCS) on TTL-heavy workloads often leads to read latency degradation and tombstone accumulation.

To solve this at massive scale, wide-column stores employ the Time Window Compaction Strategy (TWCS):

  • Time-Bucketed SSTables: TWCS groups data into discrete time windows based on the write timestamp.
  • Isolation of Eras: Data written together remains in the same SSTable. Because the rows within a specific window typically share similar TTL values, all rows in that SSTable expire at roughly the same time.
  • Instant Disk Reclamation: Once the newest record in an SSTable passes its TTL and the grace period expires, the storage engine deletes the entire SSTable file instantly via a lightweight file-system unlink call, avoiding heavy disk I/O and preventing tombstone overhead during queries.
