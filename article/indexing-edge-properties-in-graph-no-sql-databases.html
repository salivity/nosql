Indexing Edge Properties in Graph NoSQL Databases

Graph NoSQL databases model rich domains by assigning key-value attributes not just to nodes, but directly to the edges connecting them. To query these edge properties efficiently without scanning the entire graph, modern graph platforms implement specialized indexing strategies ranging from global secondary indexes to edge-aware adjacency lists and integrated search engines. This article examines the underlying mechanisms graph databases use to index, store, and quickly retrieve property attributes attached to graph edges.

The Challenge of Edge Property Indexing

In labeled property graphs, edges (or relationships) represent directed connections between vertices that also hold metadata, such as weights, timestamps, or relationship types. While traditional graph traversal relies on "index-free adjacency"—where vertices directly reference their incident edges via memory or disk pointers—traversals frequently require filtering by edge properties (e.g., finding all TRANSFERRED edges where amount > 10000). Without indexing on these properties, the engine would have to perform full relationship scans across the entire database or inspect every edge attached to a node, creating significant I/O bottlenecks.

Global Secondary Indexes on Edges

Most graph engines (such as Neo4j, TigerGraph, or JanusGraph) implement global secondary indexes for relationship properties.

  • B-Trees and B+ Trees: Often used for range queries and exact lookups (e.g., timestamps or numerical weights). The tree index maps the edge property value to a set of internal edge IDs. When an edge-filtered query executes, the engine queries the B-Tree to retrieve matching edge identifiers, which are then resolved to their source and target vertices.
  • Log-Structured Merge-Trees (LSM-Trees): Used by graph systems layered over distributed key-value stores (such as JanusGraph on Cassandra or RocksDB). Property updates are written sequentially to write-ahead logs and immutable memtables, providing high-write throughput for dynamic relationship updates.

Local Edge Indexes and Composite Adjacency Structures

To optimize traversals from a specific node without scanning a global index, graph databases employ localized indexing techniques:

  • Vertex-Centric Indexes (Edge-Centric Indexes): In graphs with "supernodes" (nodes with thousands or millions of connections), filtering edges attached to a single vertex becomes a performance issue. A vertex-centric index creates a local index per vertex, ordering its incident edges by label and specific property values (e.g., sorting a user's FOLLOWS edges by created_at). This enables \(O(\log k)\) lookup times for filtering a node's edges, where \(k\) is the degree of that specific node.
  • Compound Keys in Adjacency Lists: Some native engines sort the underlying relationship records on disk by combining the relationship type with critical edge properties. For example, an edge record may be physically sequenced by [Source_ID, Edge_Type, Timestamp, Target_ID], turning property filtering into a continuous range read directly from storage.

Inverted and Full-Text Indexes

When edge attributes contain unstructured text or require complex multi-attribute querying, graph platforms frequently integrate dedicated search libraries (like Apache Lucene) or distributed search clusters (such as Elasticsearch or OpenSearch).

  • Inverted Index Mapping: The search engine builds an inverted index where tokens from string properties point to edge IDs.
  • Query Execution: The graph query planner delegates the text evaluation to the search engine, retrieves a candidate list of edge IDs, and hydrates the corresponding relationship objects in the graph execution pipeline to continue traversal.

Storage and Maintenance Overhead

Indexing edge properties involves trade-offs:

  1. Write Amplification: Updating an edge property requires updating the edge storage record and any associated global or vertex-centric index structures.
  2. Memory Footprint: Because graphs often have an order of magnitude more edges than nodes, indexing edge properties demands significantly more memory and cache allocation than node-only indexing.
  3. Traversal vs. Lookup Balance: Query planners must dynamically choose whether to traverse pointers and filter edge properties in memory (beneficial for low-degree nodes) or consult secondary edge indexes first (beneficial when the filter is highly selective across the entire graph).
