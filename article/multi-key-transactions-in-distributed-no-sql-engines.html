Multi-Key Transactions in Distributed NoSQL Engines

Key-value NoSQL databases achieve high throughput and horizontal scalability by partitioning data into discrete hash slots or shards distributed across multiple cluster nodes. However, executing transactions that span keys in different slots requires coordinating multiple isolated machines while maintaining Atomicity, Consistency, Isolation, and Durability (ACID). This article examines the core mechanisms—distributed consensus, two-phase commit protocols, timestamp ordering, and intent tracking—that modern distributed key-value engines rely on to execute multi-key transactions safely across distributed slots.

Hash Slot Partitioning and the Cross-Slot Problem

NoSQL engines partition key spaces into a fixed number of logical slots (for example, 16,384 in Redis Cluster) or dynamic ranges (as in CockroachDB and TiKV). Each slot is assigned to a specific storage node or replication group.

When an operation touches a single key or multiple keys assigned to the same slot, the transaction is executed locally using conventional, low-overhead in-memory locking or single-node concurrency control. When a transaction touches keys mapped to different slots on distinct machines, the database cannot rely on shared memory or local locks. It must orchestrate execution across the network, guarding against network partitions, partial machine crashes, and concurrent conflicting writes.

The Consensus-Backed Two-Phase Commit (2PC)

Traditional distributed systems relied on standard Two-Phase Commit (2PC), which was prone to blocking if the coordinator node failed. Modern distributed NoSQL engines solve this vulnerability by layering 2PC on top of distributed consensus algorithms like Raft or Paxos.

  1. Transaction Coordination: A designated node—often the node that received the request or a dynamically chosen leader—acts as the transaction coordinator.
  2. Phase 1 (Prepare): The coordinator sends write requests to the Raft/Paxos leader of each slot involved. Rather than writing permanently, the target slots validate the operations, acquire local locks on the keys, and write an immutable "prepare" entry to their local consensus logs. Once replicated across their local quorums, each participant votes "ready" back to the coordinator.
  3. Phase 2 (Commit): If all participants vote ready, the coordinator logs a "commit" state in its own consensus group and broadcasts the commit command to all participating slots. Each slot applies the changes permanently, releases locks, and acknowledges completion.

Because the coordinator's state and each participant's prepared state are replicated via Raft or Paxos, a crash of any single machine allows a surviving replica to pick up the transaction and safely drive it to either a complete commit or a rollback.

Write Intents and Concurrency Control

To manage isolation across distributed slots, engines typically use Multi-Version Concurrency Control (MVCC) combined with write intents.

When a multi-key transaction enters the prepare phase:

  • Provisional Records: Instead of overwriting data immediately, the engine writes a provisional value (often called an "inline lock" or "write intent") next to the key, tagged with the transaction’s unique ID.
  • Conflict Resolution: If another transaction attempts to read or write that key, it detects the intent. The reading transaction consults the coordinator’s state machine. If the transaction holding the intent is still pending, the reader either blocks, aborts itself, or pushes the pending transaction to abort depending on priority rules (e.g., Wound-Wait or Wait-Die deadlock prevention schemes).
  • Intent Resolution: Once the commit phase succeeds, the intents are upgraded asynchronously to standard committed MVCC versions, clearing the path for subsequent operations.

Timestamp Synchronization and Ordering

Ensuring strict serializability or snapshot isolation across distributed slots requires establishing an agreed-upon temporal order for transactions without a centralized bottleneck. Engines resolve this using two primary approaches:

  • Hybrid Logical Clocks (HLCs): Databases like CockroachDB and YugabyteDB combine physical time with Lamport logical counters. HLCs ensure that causally related events always reflect an ascending timestamp order even if physical system clocks exhibit minor drift.
  • Centralized Timestamp Oracles (TSO): Engines like TiKV (via PingCAP's Placement Driver) utilize a centralized, highly optimized hardware or software service that issues strictly monotonically increasing timestamps for every transaction's read and commit phases.

By attaching these global timestamps to writes, each slot independently determines whether a read operation should observe a particular version of a key, guaranteeing consistent read snapshots across all slots without distributed read-locks.

Hash Tags for Partition Colocation

Because cross-slot transactions incur network round-trips and consensus overhead, many key-value systems provide a client-side routing optimization known as hash tagging. By placing a specific substring in curly braces within the key (for example, {user_101}:profile and {user_101}:settings), the hash algorithm operates strictly on the bracketed string. This forces both keys to land in the exact same slot, reducing what would otherwise be a complex, multi-node distributed transaction into a low-latency, single-node atomic operation.
