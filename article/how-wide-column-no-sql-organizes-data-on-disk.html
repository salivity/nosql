How Wide-Column NoSQL Organizes Data on Disk

Wide-column NoSQL databases—such as Apache Cassandra, ScyllaDB, and Google Bigtable—organize data on physical media using Log-Structured Merge-tree (LSM-tree) architectures rather than the in-place update models used by relational databases. Instead of writing directly to fixed disk pages, these systems convert write operations into sequential disk writes stored in immutable, sorted files commonly known as SSTables (Sorted String Tables). This architecture arranges physical data blocks sequentially by partition key and clustering key, utilizing accompanying index files, compression offsets, and Bloom filters to enable rapid data retrieval directly from storage media.

The In-Memory Buffer to Disk Pipeline

Data organization on physical media begins in memory. When a write occurs, it is appended sequentially to a commit log for durability and written to an in-memory data structure called a memtable, which sorts records by partition token and clustering columns.

Once the memtable reaches a configured size threshold, it is flushed sequentially to persistent storage as an immutable SSTable. Because the data is already sorted in memory, the database writes it to the physical media in a single, contiguous sequential I/O operation. This eliminates random disk writes, maximizing write throughput and longevity on both HDDs and solid-state drives (SSDs).

Physical Block Layout Within SSTables

An SSTable on disk is composed of multiple physical files working together to locate and read data blocks efficiently:

  1. The Data File: This file contains the actual row records organized into compressed blocks (typically 4 KB to 64 KB in size). Within each block, records are laid out hierarchically:
    • Partition Key: Defines the boundary of a logical wide row.
    • Row Header: Contains metadata such as timestamps, deletion markers (tombstones), and row-level flags.
    • Columns/Cells: Individual attributes stored as key-value-timestamp triplets, sorted physically by their clustering keys.
  2. The Compression Offset Map: Because data blocks are compressed using algorithms like LZ4 or Zstandard to save space, physical byte offsets within the data file do not map linearly to uncompressed offsets. A companion file maps logical block offsets to exact physical byte positions on the media.
  3. The Index File: This file stores partition keys alongside their physical byte offsets in the data file. For wide rows with thousands of columns, row indexes or column indexes within the index file provide sub-offsets to specific clusters of cells, allowing the database to jump directly to a subset of data within a large partition without scanning the entire physical sequence.
  4. The Index Summary and Bloom Filter: To minimize physical disk seeks, an index summary (a sparse, sampled version of the primary index) and a Bloom filter are stored in memory or mapped directly from disk. The Bloom filter determines with high mathematical certainty if a partition key exists in a particular physical SSTable before executing a storage read.

Physical Read Operations

When a read request targeting a specific partition key and column arrives:

  1. The database checks the in-memory Bloom filter to confirm the SSTable likely contains the partition.
  2. The index summary directs the search to the nearest offset in the primary index file on disk.
  3. The index file yields the exact physical byte position of the target data block in the data file.
  4. The database reads only the specific compressed block into memory, decompresses it, and reads the sorted clustering keys sequentially until it finds the requested value.

Compaction and Block Reorganization

Because SSTables are immutable, updates and deletes do not overwrite data blocks in place; updates write a new version with a newer timestamp, and deletes write a tombstone marker. Over time, multiple SSTables hold redundant or superseded blocks on the physical media.

To maintain performance and recover disk space, the database runs background compaction processes. Compaction reads multiple physical SSTables sequentially, performs a merge sort based on the sorted keys and timestamps, discards overwritten data and expired tombstones, and writes a completely new, sequentially ordered SSTable block layout back to the storage device. Once written, the old physical files are unlinked and freed.
