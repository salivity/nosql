Non-Blocking Snapshots in NoSQL Key-Value Engines

Modern NoSQL key-value engines achieve high-availability persistent snapshots without halting write operations by decoupling data reading from active mutations. Through core mechanisms such as immutable storage architectures (LSM-trees), OS-level Copy-on-Write (CoW) memory forking, and Multi-Version Concurrency Control (MVCC), these engines create an isolated point-in-time view of the dataset. This allows background threads or external processes to flush a consistent state to durable storage while the foreground engine continues processing incoming writes at full throughput.

Log-Structured Merge-Trees and Storage Immutability

The majority of high-throughput key-value engines (such as RocksDB and Cassandra) utilize Log-Structured Merge-tree (LSM) architectures, where data immutability is fundamental.

When a write arrives, the engine appends it to an in-memory buffer called a MemTable and logs it sequentially to a Write-Ahead Log (WAL). When a snapshot is triggered:

  1. The engine switches the current active MemTable into a read-only state and immediately allocates a brand-new MemTable to receive continuous incoming writes.
  2. The data already persisted to disk lives in immutable files known as SSTables (Sorted String Tables). Because existing SSTables are never modified in place—only merged and rewritten during background compaction—their contents will not be altered by concurrent writes.
  3. The engine creates lightweight metadata references (often implemented using filesystem hard links or manifest file pointers) to the immutable SSTables and the frozen MemTable.

Because the files representing the point-in-time state cannot be modified, background processes can safely serialize or back them up without requiring locks on write paths.

Copy-on-Write (CoW) Process Forking

In-memory key-value stores with persistence capabilities, such as Redis (via RDB snapshots), leverage the host operating system’s virtual memory management via the fork() system call.

When a background snapshot initiates:

  1. The database process invokes fork(), generating an exact child process duplicate of the running instance.
  2. Rather than duplicating physical memory immediately, the OS marks all memory pages as read-only and shares them between the parent and child process via Copy-on-Write.
  3. The child process reads this frozen memory map sequentially and writes it to a persistent snapshot file on disk.
  4. When incoming writes hit the parent process, the underlying operating system transparently duplicates the specific memory pages being altered. The parent writes to the newly allocated page, while the child's view of the original page remains untouched.

This process enables full-speed writes with the only overhead being the incremental memory allocation needed for mutated pages during the snapshot window.

Multi-Version Concurrency Control (MVCC) and Sequence Numbers

Engines that do not rely strictly on process-level forking often implement MVCC by assigning every write operation a monotonically increasing sequence number or logical timestamp.

  1. When a snapshot is requested, the engine records the current maximum sequence number (often called the Snapshot Sequence Number).
  2. Concurrent write operations continue unhindered, but their updates are assigned higher sequence numbers than the snapshot marker.
  3. The background snapshot reader traverses the dataset using a filter that only processes record versions with a sequence number less than or equal to the recorded snapshot threshold.
  4. If an existing key is updated or deleted during the snapshot run, the database retains the older historical version of the record until the snapshot reader has finished writing the baseline data to disk.

Once the snapshot is complete, standard background compaction and garbage collection routines clean up the superseded versions, leaving performance unaffected throughout the snapshot lifecycle.
