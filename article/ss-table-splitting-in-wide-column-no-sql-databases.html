SSTable Splitting in Wide-Column NoSQL Databases

Wide-column NoSQL databases manage growing datasets by pairing immutable storage with background maintenance processes known as compaction. Because Sorted String Tables (SSTables) are strictly read-only once written to disk, databases cannot split an existing SSTable file in place. Instead, the database uses automated compaction cycles to merge overlapping key ranges, purge deleted data, and divide large sequential datasets into smaller, balanced SSTable files based on predetermined size limits or partition boundaries.

The Role of LSM-Trees and Immutability

Wide-column systems such as Apache Cassandra, ScyllaDB, and Google Bigtable rely on Log-Structured Merge-trees (LSM-trees). Writes first enter an in-memory buffer (the Memtable) and an append-only commit log. When the Memtable fills, the database flushes it to disk as a sorted, immutable SSTable.

Because existing SSTables cannot be modified, data modifications and deletions (tombstones) are written as new entries in newer SSTables. Over time, this creates fragmentation and duplicate entries across multiple files. Automated background compaction resolves this fragmentation by continuously reading older SSTables and synthesizing their contents into fresh, consolidated files.

How the Splitting Mechanism Works During Compaction

SSTable "splitting" occurs naturally as a database streams and rewrites sorted data during background compaction. Rather than dividing an active file directly, the database performs a sequential streaming operation that partitions the output:

  1. Multi-Way Merge: The database identifies candidate SSTables scheduled for compaction and initializes a multi-way merge sort across their sorted keys.
  2. Filtering: During the merge, the system evaluates timestamps, discards superseded column values, and removes tombstones that have exceeded their grace period.
  3. Threshold Monitoring: As surviving rows are streamed into a new output buffer, an internal counter tracks the cumulative byte size or partition count of the file being written.
  4. Boundary Rollover: When the output file hits a configured target threshold (such as a maximum file size or a primary key boundary), the writer finalizes the current SSTable. It generates the primary index, bloom filter, and summary file, then immediately opens a new, distinct SSTable file to receive the remaining sorted records.
  5. Metadata Update and Cleanup: Once the entire stream has finished writing to the set of newly split SSTables, the database commits a metadata transaction (often in a system manifest) to register the new files and atomically unlinks the old, larger SSTables.

Splitting Strategies Across Compaction Types

Different compaction strategies handle file boundaries differently depending on operational priorities:

Leveled Compaction (LCS)

In Leveled Compaction, data is organized into exponential tiers (L0, L1, L2, etc.). Each level from L1 onward represents non-overlapping key ranges with fixed-size SSTables (typically 160 MB in Cassandra). When an SSTable from L1 merges with overlapping SSTables in L2, the output cannot exceed the level's standard size limit. The database continuously closes the current SSTable file and opens a new one every time the 160 MB mark is reached, generating a series of uniformly split, non-overlapping SSTables.

Size-Tiered Compaction (STCS)

Size-Tiered Compaction groups SSTables of similar sizes together. While STCS primarily consolidates smaller files into larger ones, modern engines split output files if the resulting merge would exceed maximum file-size limits or when executing specialized operations like split compactions to alleviate operational overhead.

Region and Tablet Splitting (Bigtable and HBase)

In systems like Google Bigtable or Apache HBase (which uses HFiles, an SSTable variant), datasets are managed across distributed nodes by key-range units called tablets or regions. When an individual tablet grows beyond a defined storage limit (e.g., several gigabytes), a split is triggered.

During the split operation, the database identifies a midpoint row key. Compaction processes write the data below the split key into a new tablet's SSTables and the data above the split key into another. This redistributes the storage footprint and allows the cluster to move one of the split tablets to a different physical node.

Operational Advantages of Automated Splitting

Splitting SSTables during maintenance cycles prevents several performance bottlenecks:

  • Predictable Read Latency: Smaller, bounded SSTables combined with bloom filters reduce disk seeks, as readers inspect fewer index blocks per query.
  • Balanced Disk Space Reclamation: Splitting ensures that tombstones are contained within smaller chunks of data, allowing the database to clear obsolete disk space more frequently without waiting to rewrite massive multi-gigabyte files.
  • Efficient Backup and Repair: Managing data in modular, uniformly sized files reduces I/O spikes when streaming data between replicas during node repair, rebalancing, or incremental backups.
