Why Event Sourcing Uses Append-Only NoSQL Stores

This article explores why modern event sourcing architectures consistently rely on append-only NoSQL data stores instead of traditional relational databases. It examines how the intrinsic properties of event sourcing—namely immutability, entity-based partitioning, and high write volumes—align with the strengths of NoSQL systems, including sequential write performance, horizontal scalability, schema flexibility, and built-in partition tolerance.

Natural Alignment with Immutability

Event sourcing models system state as an immutable sequence of domain events that represent historical facts. Because facts cannot change, these systems strictly perform append operations and never update or delete historical records. Append-only NoSQL stores enforce this behavioral invariant at the storage engine level. By avoiding the overhead of in-place row updates and complex referential integrity constraints, these databases eliminate the risk of accidental mutations and guarantee an accurate, tamper-proof audit log.

Superior Write Throughput via Sequential I/O

Because event-sourced applications capture every state transition as a new event, they generate significantly higher write traffic than traditional Create, Read, Update, Delete (CRUD) applications. Many NoSQL engines use Log-Structured Merge-trees (LSM-trees) or write-ahead logs that optimize specifically for sequential disk writes. Appending an event to a NoSQL store requires zero random disk I/O, no multi-table relational foreign key verification, and no index-rebalancing operations. This enables systems to achieve sub-millisecond latencies under massive concurrent write workloads.

Linear Horizontal Scaling and Natural Partitioning

Event streams are inherently bounded by the lifecycle of a domain aggregate, such as an order, user account, or billing cycle. To preserve total order, events only need to be ordered strictly within the boundary of a single aggregate ID, not globally across the entire system. Distributed NoSQL stores are architected around partition keys (hash rings). By using the Aggregate ID as the partition key, the event store distributes streams uniformly across a cluster. This architecture allows write throughput to scale linearly simply by adding nodes to the database cluster.

Painless Schema Evolution

Domain models and event definitions inevitably change over time. Historical events written years ago may have a completely different structure than events produced today. Rigid relational schemas struggle with polymorphically storing multiple versions of distinct event types in a single table without resorting to bloated null-filled columns or complex mapping layers. Document-oriented and key-value NoSQL stores persist payload data natively as schemaless formats like JSON, Protobuf, or BSON, allowing multiple schema versions to coexist within the same aggregate stream without requiring blocking database migrations.

Efficient Optimistic Concurrency Control

To prevent state corruption, an event store must ensure that two conflicting commands do not append an event to the same aggregate stream concurrently. Distributed NoSQL stores typically offer atomic single-key transactions or conditional write operations (e.g., conditional put if version equals \(N\)). Because the concurrency boundary matches the NoSQL document or partition key boundary, optimistic locking is achieved cleanly and efficiently without the need for heavyweight, distributed, two-phase commit database locks.
