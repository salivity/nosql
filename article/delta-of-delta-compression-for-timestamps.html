Delta-of-Delta Compression for Timestamps

Time-series NoSQL databases process massive volumes of sequential data points, where timestamps alone can consume substantial storage if stored as raw 64-bit integers. Delta-of-delta encoding solves this scalability bottleneck by calculating the difference between consecutive time intervals rather than storing absolute values. This article explains how delta-of-delta compression works, why it achieves extreme compression ratios on periodic time-series metrics, and why modern distributed engines like Prometheus, InfluxDB, and Facebook's Gorilla rely on it to optimize storage and query throughput.

The Problem with Raw Timestamps

In time-series workloads, every metric value requires an associated timestamp. Standard Unix timestamps are typically represented as 64-bit integers (int64) to preserve nanosecond or millisecond precision. Storing billions of metrics per day means that raw timestamps alone quickly demand gigabytes of disk and memory, degrading cache efficiency and increasing I/O overhead.

How Delta Encoding Falls Short

A basic approach to reducing timestamp size is simple delta encoding. Instead of storing absolute timestamps (\(T_n\)), the database records the difference between consecutive timestamps:

\[D_n = T_n - T_{n-1}\]

While simple delta encoding reduces absolute values from 64-bit integers to smaller numbers, it still requires multiple bytes per entry if the interval fluctuates slightly or if the sampling rate is coarse. Furthermore, standard variable-byte encoding does not maximize efficiency when the sampling rate is largely predictable.

How Delta-of-Delta Encoding Works

Most time-series data is collected at fixed intervals (such as every 10, 30, or 60 seconds). Because the time between readings (\(D_n\)) is nearly constant, the change in the delta—the "delta-of-delta" (\(D'_n\))—is frequently zero:

\[D'_n = D_n - D_{n-1} = (T_n - T_{n-1}) - (T_{n-1} - T_{n-2})\]

Consider an agent sending metrics every 10 seconds:

  • Absolute Timestamps: 1600000000, 1600000010, 1600000020, 1600000030
  • Deltas (\(D\)): 10, 10, 10
  • Delta-of-Deltas (\(D'\)): 0, 0

When network jitter or latency causes small variations (e.g., intervals of 10s, 11s, 9s), the delta-of-deltas remain very close to zero (\(+1\), \(-2\)).

Variable-Length Bit Packing

Delta-of-delta values cluster heavily around zero, making them ideal candidates for variable-length bit packing. As popularized by Facebook's Gorilla paper, time-series stores use an encoding scheme that maps the delta-of-delta into variable-sized bit buckets:

  • If \(D' = 0\): Store a single 0 bit.
  • If \(-63 \le D' \le 64\): Store the bit prefix 10, followed by 7 bits of value.
  • If \(-255 \le D' \le 256\): Store the bit prefix 110, followed by 9 bits of value.
  • If \(-2047 \le D' \le 2048\): Store the bit prefix 1110, followed by 12 bits of value.
  • Otherwise: Store the bit prefix 1111, followed by the full 32-bit value.

Under consistent collection intervals, a timestamp requires only a single bit of storage instead of the original 64 bits.

Why Time-Series NoSQL Stores Rely on It

  1. Extreme Compression Ratios: In real-world environments where agents emit heartbeats or metrics periodically, timestamps compress by over 95%, frequently averaging around 1.37 bits per timestamp.
  2. Reduced Disk and Memory Footprint: Shrinking timestamps allows databases to retain active working sets entirely in RAM, significantly accelerating read queries over historical ranges.
  3. Optimized Scan Performance: Decompressing simple bit-shift and addition operations is computationally lightweight, allowing CPUs to scan and filter billions of rows per second directly from memory without saturating bus bandwidth.
  4. Resilience to Jitter: Unlike rigid run-length encoding that breaks whenever an interval deviates slightly, delta-of-delta smoothly accommodates network delays by falling back to slightly wider bit buckets without discarding the compression scheme.
