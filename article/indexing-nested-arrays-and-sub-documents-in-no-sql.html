Indexing Nested Arrays and Sub-Documents in NoSQL

NoSQL document databases provide high performance on complex, hierarchical datasets by employing specialized indexing strategies for embedded structures. Rather than requiring users to normalize data, these engines utilize path-based dot-notation indexing for sub-documents and multikey or inverted indexing techniques for nested arrays. This article examines the mechanics of how document stores traverse, index, and query these deeply nested structures, along with the performance trade-offs associated with index size and write amplification.

Indexing Nested Sub-Documents

Sub-documents (embedded objects) represent parent-child relationships within a single record. Document databases index these structures in two primary ways:

  1. Targeted Field Indexing (Dot Notation):
    The most common and performant approach is indexing a specific attribute within the embedded document using a path expression (e.g., address.zipCode). The database treats the path as a distinct key within its underlying B-tree or LSM-tree structure. When an entry is written, the engine navigates to the specified path, extracts the scalar value, and maps it directly to the root document’s identifier. Queries targeting address.zipCode can traverse the index tree directly, bypassing the need to read or deserialize the parent document.

  2. Whole Sub-Document Indexing:
    Most document stores also allow you to index the entire sub-document object (e.g., indexing address). In this case, the database serializes the entire nested structure into a single binary representation (such as BSON or JSON). However, querying an index on a whole sub-document requires an exact match, including field order. If a query provides { city: "Austin", zipCode: "78701" }, but the document stored it as { zipCode: "78701", city: "Austin" }, the index match will fail unless the engine normalizes key ordering before hashing or tree insertion. Consequently, whole-document indexing is rarely recommended over targeted path indexing.

Indexing Nested Arrays (Multikey Indexes)

Arrays introduce cardinality challenges because a single document field can contain zero, dozens, or thousands of values. Document engines handle this via multikey indexing.

  • Array Flattening in the Index:
    When an index is created on an array field (e.g., tags), the database creates a separate index entry for every individual element in that array. If a document has the tags ["database", "nosql", "indexing"], the engine adds three distinct entries into the index structure, all pointing back to the same parent document ID.
  • Arrays of Sub-Documents:
    When indexing an array of objects (e.g., items.sku), the engine traverses each object in the array, extracts the specified field, and generates an index entry for each scalar value found. A query filtering for items.sku = "A123" performs a fast lookup in the index to locate any document containing an array element with that SKU.

Indexing Limitations and Cartesian Explosion

To maintain efficiency, document stores impose strict rules on array indexing:

  • Compound Index Restrictions:
    Most document databases (such as MongoDB) forbid compound multikey indexes where more than one field is an array. For example, you cannot create a compound index on users.tags and users.emails if both are arrays within the same document. Allowing this would result in a Cartesian product of index entries (e.g., an array of 20 tags and 5 emails would produce 100 index entries for a single document), leading to severe index bloat and extreme write latency.
  • Write Amplification:
    Because an array with \(N\) elements creates \(N\) index keys, appending to or modifying an array incurs high write overhead. Updating an embedded list requires the database to remove old index keys and insert new ones across the index tree.

Underlying Data Structures

Most document stores use B-Trees or Log-Structured Merge-Trees (LSM-Trees) to store path-indexed scalar values and multikey array elements. Search-oriented document stores (such as Elasticsearch) instead use Inverted Indexes, mapping array tokens to a posting list of document IDs. Regardless of the underlying structure, the fundamental strategy remains consistent: the database unpacks nested paths and array elements at write time so that lookups can occur in logarithmic time rather than requiring a full collection scan.
