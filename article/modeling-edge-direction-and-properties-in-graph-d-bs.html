Modeling Edge Direction and Properties in Graph DBs

This article provides an overview of how graph NoSQL databases represent and manipulate relationships between entities. It explores the mechanics of edge directionality, detailing how systems store directed connections while allowing flexible bidirectional traversals. Additionally, it examines how modern property graph models assign rich metadata—such as weights, timestamps, and contextual attributes—directly to relationship edges as first-class citizens without sacrificing traversal performance.

The Foundation: The Property Graph Model

Most native graph NoSQL databases (such as Neo4j, Amazon Neptune, and Memgraph) implement the Labeled Property Graph (LPG) model. In an LPG, data consists of nodes (entities), relationships (edges), labels (categories), and properties (key-value pairs).

Unlike relational databases that simulate relationships using foreign keys and join tables, graph systems treat edges as first-class, independent entities. An edge must have a unique identifier, an explicit start node, an explicit end node, and a type label that defines the nature of the connection.

How Graph Databases Model Edge Directionality

Graph NoSQL systems predominantly enforce directed graphs at the storage layer. Every edge physically points from a source node (tail) to a target node (head).

Storage Mechanism and Index-Free Adjacency

To model direction efficiently, graph databases employ index-free adjacency. Each node directly holds references (pointers) to its incoming and outgoing edges, typically organized as doubly linked lists or compact arrays:

  • Outgoing pointers: A node maintains an out-edge pointer pointing to the first relationship where it acts as the source.
  • Incoming pointers: A node maintains an in-edge pointer pointing to the first relationship where it acts as the target.
  • Edge records: Each edge record stores the memory addresses of its source node, target node, the next outgoing edge for the source, and the next incoming edge for the target.

Bidirectional Traversal

Although every edge is strictly directed in storage, graph query engines (like Cypher or Gremlin) decouple logical traversal from physical direction. Traversal algorithms can navigate:

  • Outbound: Traversing from source to target.
  • Inbound: Traversing from target to source.
  • Undirected: Traversing regardless of direction.

Because incoming and outgoing pointers are indexed at the node level, moving against the edge direction incurs no performance overhead. Consequently, modeling truly symmetric relationships (such as a "friendship" or "sibling" relation) rarely requires creating two opposing edges. Engineers typically create a single directed edge and query it without specifying direction.

Modeling Properties on Relationship Edges

In many data models, relationships carry vital contextual information that cannot logically belong to either connected node. Graph databases solve this by allowing edges to hold key-value attributes directly.

Internal Edge Property Representation

Edge properties are stored similarly to node properties:

  1. Pointer to Property Chains: The edge record contains a property pointer addressing a singly linked list or block of property records in a dedicated property store file.
  2. Key-Value Pairs: Each property record holds a key (often resolved via an internal schema dictionary to save space), the primitive data type, and the value (or a pointer to dynamic storage for large strings and arrays).
  3. Immutability and Modification: Updating or adding a property to an edge modifies these property chains without changing the structural pointers between the connected nodes.

Practical Schema Example

Consider a transaction in an e-commerce context:

  • Node A: (:Customer {id: "cust_123", name: "Alice"})
  • Node B: (:Product {sku: "PROD_99", name: "Laptop"})
  • Edge: [:PURCHASED {order_id: "ORD_789", timestamp: 1698240000, price: 1299.99, status: "completed"}]

In this example, the edge represents both the association and the transaction data. Filtering queries by edge attributes—such as finding all purchases over $1,000 made in the last month—evaluates these properties during relationship traversal rather than through heavy relational joins.

Advantages Over Alternative Architectures

The ability to natively store properties and direction on edges distinguishes property graphs from other paradigms:

  • Versus Relational Databases: Eliminates costly multi-table joins. In an RDBMS, edge properties require a distinct join table with its own primary and foreign key indexes.
  • Versus Basic RDF Triples: Traditional Resource Description Framework (RDF) models store data as Subject -> Predicate -> Object. They cannot naturally attach properties to predicates without complex reification or the newer RDF-star extension.
  • Query Efficiency: Edge properties allow query engines to prune traversal paths early. If an algorithm seeks paths where an edge property satisfies a condition (such as distance < 50), it can discard irrelevant subgraphs immediately upon inspecting the edge record.
