Resource Allocation in NoSQL Background Compaction

This article examines how distributed NoSQL databases prevent background data compaction from degrading read and write performance. It explores core mechanisms including I/O rate limiting, isolated thread pools, memory-cache bypassing, dynamic resource scheduling, and strategy selection. By balancing system maintenance with incoming traffic demands, modern NoSQL systems maintain strict latency service-level objectives (SLOs) even under write-heavy workloads.

The Compaction Dilemma in LSM-Tree Databases

Most write-optimized NoSQL databases—such as Apache Cassandra, ScyllaDB, RocksDB, and Google Cloud Bigtable—utilize Log-Structured Merge-trees (LSM-trees). Writes are appended sequentially to an in-memory buffer (MemTable) and periodically flushed to immutable disk files (SSTables).

Over time, multiple SSTables accumulate, creating duplicate keys, obsolete records, and deletion markers (tombstones). Background compaction reads multiple SSTables, merges and sorts the data, drops stale keys, and writes clean, consolidated files. While critical for maintaining fast read performance and reclaiming disk space, this process consumes significant CPU, disk I/O, and memory bandwidth, potentially starving user-facing queries.

I/O Throttling and Rate Limiting

To prevent background merge operations from saturating storage subsystems, databases implement strict I/O throughput limits:

  • Token Bucket Algorithms: Systems like RocksDB and Apache Cassandra use token bucket limiters to meter compaction write speeds. Administrators or automated systems assign a compaction throughput cap (for example, limiting compaction writes to 64 MB/s per node).
  • Write Burst Handling: By defining maximum burst sizes, systems ensure that temporary spikes in compaction activity do not overwhelm the underlying SSD or NVMe drives, preserving random-read IOPS for live user queries.

Thread Isolation and OS Prioritization

NoSQL architectures isolate compaction workloads from client read/write pipelines using multi-threading and process-priority controls:

  • Separated Thread Pools: Work is segregated across dedicated thread pools. Incoming client requests execute on high-priority request pools, while compaction tasks run in low-priority worker pools.
  • CPU Nice Levels and Scheduling: Background compaction threads can be assigned higher nice values at the OS level, instructing the Linux kernel scheduler to yield CPU cycles to query-processing threads whenever a scheduling conflict occurs.
  • Core-Per-Thread Partitioning: Modern C++-based architectures (such as ScyllaDB, built on the Seastar framework) dedicate CPU cores to specific shards. Inside each shard, a user-space scheduler dynamically allocates a specific percentage of execution time (shares) to compaction versus request processing.

Dynamic Resource Scheduling

Static rate limits often underutilize hardware during off-peak hours and fail to react fast enough during sudden traffic surges. Dynamic schedulers resolve this trade-off:

  • Latency-Aware Throttling: The database monitors client request latency. If read or write latencies breach defined thresholds (for instance, p99 latency exceeding 10ms), the engine automatically reduces compaction thread concurrency and lowers I/O limits.
  • Compaction Backlog Monitoring: If writes outpace compaction, the system faces "read amplification" or disk exhaustion. Dynamic engines continuously evaluate the compaction backlog; during periods of low client activity, they automatically scale up compaction limits to clear pending tasks quickly.

Memory Isolation and Cache Protection

Compaction processes large volumes of cold, historical data that should not interfere with active database caches:

  • Bypassing the OS Page Cache: Heavy sequential reads and writes during compaction can flush hot, frequently read pages out of the operating system’s page cache. Engines use flags such as O_DIRECT or POSIX cache hints (posix_fadvise with POSIX_FADV_DONTNEED) to stream compaction data without evicting cached application data.
  • Isolated Merge Buffers: Memory required for sorting and merging SSTables is allocated from distinct buffers separate from the read-cache (Row Cache, Key Cache) and write-cache (MemTables), preventing out-of-memory (OOM) errors during heavy merge phases.

Workload-Specific Compaction Strategies

Resource allocation also depends on choosing the compaction algorithm tailored to the access pattern:

  • Size-Tiered Compaction Strategy (STCS): Merges SSTables of similar sizes. It uses low CPU and disk resources during ingestion but triggers large, resource-intensive compaction events when merging huge files.
  • Leveled Compaction Strategy (LCS): Divides data into hierarchical levels with strict size limits. It imposes constant, predictable background I/O overhead to maintain high read efficiency.
  • Time-Window Compaction Strategy (TWCS): Designed for time-series data, TWCS only compacts data within a designated time window. Once a time window closes, the SSTables are never compacted again, reducing compaction resource consumption to near zero for historical records.
