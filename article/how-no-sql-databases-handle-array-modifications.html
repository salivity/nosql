How NoSQL Databases Handle Array Modifications

Document-oriented NoSQL databases optimize array modifications by avoiding full-document rewrites on disk, preventing performance bottlenecks and high input/output operations. Rather than re-serializing and writing an entire document file whenever an element is added, updated, or removed, modern document stores rely on specialized storage engines. These engines utilize techniques such as in-place updates with allocated padding, write-ahead delta logging, storage-level paging, and internal tree representations to isolate and persist only the modified array segments.

In-Memory Page Mutation and Dirty Page Tracking

Modern NoSQL platforms, such as MongoDB using the WiredTiger engine, do not write directly to document files on disk during a write operation. Instead, the document is loaded into an in-memory cache as an uncompressed representation.

When an array modification occurs (such as an append, pop, or index update):

  • The engine applies the change directly to the specific memory addresses associated with that array within the cached page.
  • The memory page containing the document is marked as "dirty."
  • The modified document remains in memory until a checkpoint process compresses and writes the dirty page back to disk in bulk.

Because updates happen in memory first, high-frequency array manipulations run with low latency without triggering immediate disk input/output.

Write-Ahead Logging and Delta Commits

To ensure durability without immediate full-document writes, databases use a Write-Ahead Log (WAL) or transaction journal. When an array is altered, the database writes a compact delta operation (a change record describing the modification, such as adding an element to a specific index) to the append-only log file on disk.

Because append operations to a sequential log are fast, the database guarantees durability immediately. If the server crashes before the modified document in memory is flushed to its primary data file, the database replays the delta logs during recovery to reconstruct the array's state.

Page-Based Block Storage and Partial Page Rewrites

Document databases store records inside fixed-size disk blocks or pages (commonly 4KB to 32KB). A document file on disk is an aggregate of these physical pages, not a single monolithic file per document.

When the database flushes a modified array to the persistent storage layer:

  1. The engine identifies the specific page containing the document.
  2. Only that individual page—or a newly allocated copy of it in copy-on-write architectures—is written to disk.
  3. The rest of the document collection files and surrounding data pages remain completely untouched.

Document Growth and Padding Allocation

When an array grows, it increases the total byte size of the document. Storage engines manage this growth using allocation strategies:

  • Pre-allocated Padding: Some engines allocate slightly more byte capacity than the document currently requires. If an array expands within this pre-allocated buffer, the update is performed strictly in-place on the existing storage block without shifting neighboring records.
  • Relocation on Overflow: If an array expands beyond the page's free space or the record's allocated boundary, the engine moves only that specific document to a new location with sufficient contiguous space, reclaiming the old space for future writes.

Structural Decomposition and Nested Trees

For documents with very large arrays, advanced storage formats decompose the document into an internal hierarchy, such as a B-tree or nested key-value pairs at the storage layer.

In these systems, array elements are stored across distinct leaf nodes rather than as a single contiguous byte array. Adding or deleting an element simply requires inserting, deleting, or rebalancing a specific leaf node within the storage engine’s internal tree structure, leaving the remaining elements and the root document structure unmodified.
