How Key-Value NoSQL Databases Store Large BLOBs

Key-value NoSQL databases are inherently engineered for low-latency retrieval of small payloads, making the handling of large binary objects (BLOBs)—such as videos, high-resolution images, and disk archives—a unique engineering challenge. To maintain high throughput and low latency without exhausting system memory or causing severe I/O bottlenecks, modern key-value architectures employ specialized techniques including reference-based separation, data chunking, LSM-tree key-value decoupling, and streaming I/O.

Decoupled Storage and Metadata Pointers

The most common architecture separates metadata from the actual binary payload. Instead of storing a multi-megabyte or gigabyte object directly inside the primary key-value store, the database stores only the metadata, access policies, and a unique content addressable identifier (URI or hash). The heavy binary payload is written directly to a dedicated distributed object store or distributed file system (such as Amazon S3, MinIO, or Ceph). This hybrid approach prevents the database's internal indexing structures from bloating and preserves cache efficiency for standard transactional operations.

Data Chunking

When a system must store binary data internally, it splits the payload into fixed-size chunks (typically between 64 KB and 255 KB). A master document or key tracks the sequence of these chunks. Chunking provides several critical performance advantages:

  • Memory Management: Servers can process and stream large files incrementally, avoiding out-of-memory (OOM) errors that occur when buffering massive payloads in RAM.
  • Network Efficiency: Clients can upload or download chunks concurrently using parallel TCP streams, and failed transfers only require resending the affected chunk rather than the entire file.
  • Balanced Sharding: Distributing chunks across different partitions prevents "hot spotting," ensuring no single storage node bears the entire I/O load of a massive file.

Key-Value Separation in Log-Structured Merge (LSM) Trees

Many high-performance key-value systems (like RocksDB and BadgerDB) use Log-Structured Merge-trees. In traditional LSM-trees, storing large values causes severe write and read amplification because large payloads are repeatedly rewritten during background compaction cycles.

To solve this, modern engines implement the WiscKey design (often termed BlobDB). The key and a small pointer are stored within the sorted LSM-tree, while the large binary value is written immediately to an append-only "Blob Log" (vLog). Compactions only reorganize the small keys and pointers, drastically reducing disk I/O and SSD wear while maintaining fast lookup speeds.

Zero-Copy and Streaming APIs

Efficient handling of large binary objects requires minimizing CPU cycles spent copying data between kernel and user space. High-performance key-value systems utilize asynchronous streaming APIs combined with operating-system-level zero-copy mechanisms (such as sendfile). These mechanisms route the binary data directly from the storage media to the network socket, bypassing application-level memory buffers entirely.

Dedicated Garbage Collection

Deleting or updating large binaries can quickly fragment physical disk space. In decoupled or chunked setups, deletion is handled asynchronously. When a key is deleted or modified, the database writes a lightweight tombstone marker. Dedicated background garbage collectors then scan the binary logs or object stores to reclaim storage space in bulk during low-traffic periods, preventing garbage collection from interfering with real-time read and write requests.
