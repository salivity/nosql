How Distributed NoSQL Engines Execute Joins

Distributed NoSQL databases traditionally favor denormalization to optimize for write throughput and horizontal scalability, but modern engines increasingly support joins across partition boundaries. Executing a join across partitions requires moving data over the network so that records with matching keys can be compared on the same physical machine. Distributed engines accomplish this through specific execution strategies, primarily broadcast joins, shuffle joins, colocated partition joins, and coordinator-driven scatter-gather operations.

The Challenge of Cross-Partition Data

In a distributed NoSQL architecture, data is split into partitions across independent nodes using hash-based or range-based partitioning keys. When two datasets must be joined on an attribute other than their shared partition key, related records typically reside on different physical servers. The engine cannot perform a local in-memory or disk comparison without first redistributing the data across the network, turning the join operation into a distributed data transfer problem governed by network bandwidth and latency.

Broadcast Joins (Replicated Joins)

A broadcast join is deployed when one of the datasets involved in the join is significantly smaller than the other.

  1. The distributed query coordinator identifies the smaller dataset (often after applying query filters).
  2. The entire small dataset is copied and transmitted across the network to every node hosting a partition of the larger dataset.
  3. Each node performs a standard local join between its local partition of the large dataset and the received copy of the small dataset.

This method minimizes cross-network communication because only the smaller table is moved, completely avoiding the need to redistribute the larger dataset.

Shuffle Joins (Repartition Joins)

When both datasets are too large to fit into memory or would cause excessive overhead if broadcast, the engine uses a distributed shuffle join:

  1. Both datasets are scanned in parallel across all cluster nodes.
  2. Nodes apply a uniform hash function to the join key of each record.
  3. Records are streamed over the network to specific destination nodes corresponding to their join key hash.
  4. Because matching join keys produce identical hashes, records from both datasets with the same key are guaranteed to arrive at the same physical node.
  5. Once data transfer is complete, each destination node executes a local hash or merge join on the received subsets.

While shuffle joins are resource-intensive due to heavy network I/O, serialization, and disk buffering, they scale horizontally for arbitrary data volumes.

Colocated Joins (Partition-Wise Joins)

Some distributed NoSQL engines bypass network transfers entirely through affinity partitioning or schema colocation. If two tables or document collections are explicitly configured to share the same partition key and partitioning strategy, records with the same key always live on the same physical shard. The engine pushes the join down directly to the local storage engine on each node, parallelizing the operation across the cluster with zero inter-node communication.

Coordinator-Driven Nested Loops

For queries targeting specific subsets via selective indexes, distributed engines frequently execute a distributed nested-loop join orchestrated by a query coordinator:

  1. The coordinator queries the driving dataset using primary or secondary indexes to retrieve a small set of matching keys.
  2. The coordinator batches these keys and issues targeted parallel remote lookups (often via multi-get or batch-fetch APIs) to the specific storage nodes hosting the corresponding records of the target dataset.
  3. The coordinator receives the raw records and stitches the results together in memory before returning them to the client.

This approach prevents massive data shuffling when queries contain highly selective filters, ensuring low-latency execution at the cost of coordinator CPU and memory utilization.
