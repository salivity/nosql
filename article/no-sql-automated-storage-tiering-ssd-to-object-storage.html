NoSQL Automated Storage Tiering: SSD to Object Storage

Modern NoSQL databases increasingly balance low-latency performance with cost efficiency by implementing automated storage tiering between local solid-state drives (SSDs) and remote cloud object storage. This article explores the architectural mechanisms that enable this process, detailing how databases manage data temperature, utilize compaction routines, separate storage compute layers, and route reads and writes across disparate storage tiers without application-level intervention.

Temperature-Based Data Classification

Automated tiering relies on continuous tracking of data temperature—classifying data as "hot," "warm," or "cold" based on access frequency, creation timestamp, or explicit lifecycle policies.

  • Hot Data: Active writes and frequently accessed records reside on local NVMe or SATA SSDs to deliver sub-millisecond read/write latencies.
  • Warm Data: Infrequently read data, often transitioning out of primary working sets, may sit on cheaper local block storage or cached SSD layers.
  • Cold Data: Historical or archival records that are rarely accessed are scheduled for migration to object stores such as Amazon S3, Google Cloud Storage, or Azure Blob Storage.

Databases evaluate access telemetry (read/write frequency counters) or temporal partition bounds (such as time-series partition drops) to determine when a given segment of data crosses the threshold from hot to cold.

LSM-Tree Integration and Compaction-Driven Migration

Many distributed NoSQL databases—including Apache Cassandra, ScyllaDB, and RocksDB-based engines—use Log-Structured Merge-tree (LSM-tree) architectures. LSM-trees naturally fit automated tiering through their periodic compaction processes:

  1. Memtable and L0 Flushes: Incoming writes land in an in-memory memtable and commit log on fast SSDs, then flush as immutable sorted string tables (SSTables) to level 0 (L0) on the SSD tier.
  2. Tiered Compaction Strategy: As data grows, background compaction merges smaller SSTables into larger ones at deeper levels (e.g., L1, L2, L3).
  3. Cross-Device Compaction: Instead of keeping all levels on local disks, the compaction controller is configured with storage classes. Once an SSTable reaches a specific depth or age threshold, the compaction worker writes the merged output directly to object storage rather than local disk.
  4. Local Metadata Retention: Even when the primary SSTable data block moves to object storage, the database retains primary keys, index summaries, and Bloom filters on the local SSD to ensure fast key-lookup resolution.

Architectural Separation of Compute and Storage

Cloud-native NoSQL designs decouple compute nodes from shared object storage to automate tiering transparently:

  • Local Disk as a Ephemeral Cache: The local NVMe SSD functions as a high-speed write buffer and read-through/eviction cache (using algorithms such as Least Recently Used, or LRU).
  • Primary Source of Truth in Object Storage: Once local blocks are synced to remote object stores, the local copy becomes an eviction candidate. If the local SSD capacity reaches a predefined high-water mark (e.g., 85% capacity), the tiering daemon flushes dirty blocks to object storage and evicts clean blocks.
  • Chunk Virtualization: File systems or engines divide tables into small chunks (often 64 MB to 128 MB). A translation layer tracks whether a chunk resides locally, remotely, or across both layers, abstracting the physical location from the query execution engine.

Handling Writes, Updates, and Immutability

Object storage services enforce write immutability—they do not allow in-place file modifications. NoSQL systems handle updates to cold data using append-only semantics:

  • Tombstones and Incremental Writes: When cold records are updated or deleted, the system does not modify the object in remote storage. Instead, it writes a delta file (or tombstone marker) to the hot SSD tier.
  • Coordinated Reads: Read requests query both the cold object store and the local delta logs, merging the results at runtime to present the current state.
  • Remote Compaction: Dedicated background workers periodically read multiple objects from cloud storage, apply local tombstones, and write consolidated, immutable objects back to the object store.

The Read Path: Caching and Range Requests

Reading from object storage introduces network latency ranging from 20 to 100+ milliseconds. Databases mitigate this penalty through optimized read-path routing:

  • Filter-First Checking: Bloom filters and index files cached on the local SSD evaluate whether an object contains the requested key before any remote network call occurs.
  • Byte-Range Fetches: When a remote read is unavoidable, engines use HTTP range requests (GET with byte offsets) to pull only the specific block or row index rather than downloading the entire multi-gigabyte data file.
  • Re-warming Blocks: Frequently read cold blocks are dynamically copied back to the local SSD tier, re-elevating their status to hot or warm until access frequencies decline again.
